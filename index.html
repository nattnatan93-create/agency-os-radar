Top 5 Discoveries

1. heldkeys — which keys is your agent holding? TEST NOW

  • Link: github.com/hugomn/heldkeys
  • What it does: a small Rust CLI that answers one question: "if a prompt injection hijacked the AI agent running here, which credentials could it use?" It lists the credentials an agent can reach — environment variables, cloud CLI logins (AWS, gcloud, Azure), AI tool logins (Claude Code, Codex, Gemini CLI, Copilot, Hugging Face), .env files and their editor backups, SSH keys, package/git tokens, and tokens pasted into MCP server configs — without ever printing a single secret. It also checks agent risks in GitHub Actions and has a --strict mode that fails like a gate.
  • What changed & when: brand-new project — repo created October 15, 2026; actively updated through October 18 (VERIFIED via GitHub).
  • Why it matters to a vibe coder: your IDE, terminals, and agents sit next to every client login you own. heldkeys turns that invisible exposure into a concrete list — the input for real least-privilege cleanup.
  • License & costs: MIT (VERIFIED from repo). Free, open source, runs fully locally, no API keys, no subscription.
  • Windows: NOT supported yet — built and tested on Linux and macOS only; on Windows use the Linux binary under WSL (VERIFIED from README FAQ). Native Windows support is on their roadmap.
  • Agency OS fit: a preflight check before any agent is allowed near a client project. Agency OS compatibility: plausible, untested.
  • Agent/stage: Security agent · SECURITY stage, and as a preflight gate before DEVELOPMENT and RELEASE.
  • Evidence/output: a credential-exposure report (severity-graded findings, e.g. "HIGH: Docker registry credentials, plaintext") — REAL evidence, no secrets leaked into the report itself.
  • Limitations/risks: it can't see browser sessions, IDE tokens, OS keychains, or unlocked password managers, and it can't tell what a token is allowed to do — a clean report means "no known exposure", not "no exposure" (README is explicit about this). Human review still decides what to revoke or move.

3. Keploy v3.6.141 — API tests from real traffic TEST NOW

  • Link: github.com/keploy/keploy
  • What it does: a developer-centric API and integration testing tool that auto-generates test cases (with mocks) from real application traffic instead of hand-written test code, then replays them; it also creates safe, isolated production sandboxes for API, integration, and E2E testing. It pitches "API tests faster than unit tests, from user traffic."
  • What changed & when: release v3.6.141 published TODAY, October 18, 2026 (VERIFIED via GitHub releases) — very high release cadence. ~18.6k stars per GitHub search on Oct 18.
  • Why it matters to a vibe coder: AI agents write features fast but regressions in API behavior are what quietly break client systems. Recording real calls and replaying them as tests gives Agency OS's API-QA layer evidence without writing hundreds of test stubs by hand.
  • License & costs: Apache-2.0 (VERIFIED from LICENSE file). The OSS tool is free; Keploy also sells a cloud/enterprise offering — not required for local use.
  • Windows: the keploy binary is Linux-native; on Windows use WSL2 (per Keploy's docs) — UNVERIFIED by me on Windows, check the official docs before installing.
  • Agency OS fit: API/integration slice of the QA stage. Agency OS compatibility: plausible, untested.
  • Agent/stage: QA agent · QA stage, plus regression evidence for RELEASE.
  • Evidence/output: generated test case files, mocks, and pass/fail test-run reports per replay.
  • Limitations/risks: recorded tests prove "same behavior as before", not "correct behavior" — someone must define what correct is; recordings can contain sensitive data that must be scrubbed before being stored as evidence.

Agency OS Integration Proposal: heldkeys as a preflight security gate

  • Problem solved: nothing currently measures what credentials an Agency OS agent could reach — the security agent would be asserting safety from an ASSUMPTION, not evidence.
  • Workflow improved: security agent's environment preflight check, run before an agent session starts on a client project.
  • Lifecycle location: SECURITY stage; also run as a preflight before DEVELOPMENT sessions and before RELEASE.
  • Inputs: none beyond the environment itself — it runs in the agent's shell context.
  • Outputs: a credential-exposure report stored as project evidence, classified REAL, with scanner version and date.
  • Validation: evidence validated before advancing: report exists, findings triaged; each finding marked VERIFIED only after a human confirms the credential is really exposed and decides revoke/move/accept.
  • On failure: with --strict, unreadable-but-present files fail the gate; HIGH findings mark the environment BLOCKED in project-state.json with the report as evidence. BLOCKED requires an explicit human waiver to proceed.
  • Gate blocking / approval: it feeds the existing gate engine as evidence — it does not replace it. Accepting an exposure (waiver) is a safety decision → human approval required, per governance rules.
  • Smallest safe experiment: in WSL, run heldkeys once in your dev environment today; save the report; have the security agent classify each finding REAL/UNVERIFIED/BLOCKED. No production change, no gate modification, ~30 minutes.

Daily Learning: Credential blast radius

  • Concept: "blast radius" is the damage possible if something goes wrong. For an AI agent, its credential blast radius is every key, login, and token it can reach from where it runs — often far more than you consciously gave it, because CLIs, .env files, and editors quietly store logins on your machine.
  • How an AI agent might get it wrong: it assumes it only has the credentials it was explicitly handed ("I only have the API key in my config"), and reports the environment as safe based on that assumption.
  • How you recognize the failure: a security claim with no scan artifact behind it; an evidence item classified VERIFIED that is actually an ASSUMPTION.
  • Which tool/test detects it: heldkeys (today's test) enumerates the real blast radius without printing secrets; your rule: no agent environment is declared safe without a stored, dated scan report.
