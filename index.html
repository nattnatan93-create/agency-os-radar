The problem: when an AI agent says a job is "done", the only witness is the agent itself. For a solo vibe coder juggling client work, that is the weak link: the code might pass the agent's own summary while the actual requirement is half-met, the ticket nobody updated, and the reason a choice was made lost the moment the session ended.

Nothing grades its own homework, and everything lands on your own infrastructure against your own tracker.

The Featured Factory: holgerleichsenring/agent-smith ("codeably") — ticket in, spec, evidence-checked pull request out TEST NOW

  • Link: github.com/holgerleichsenring/agent-smith · written in C# on .NET 10 · ships as a single-binary CLI (Linux x64/ARM64, macOS Intel/Apple Silicon, Windows), Docker Compose server, or Kubernetes · skills live in a separate repo (agent-smith-skills) and ship embedded in each release.
  • Name note: the project was called Agent Smith until November 2026; the CLI, the agentsmith.yml config and the repo name still carry it. Facts below are from the current repo.
  • License (verified from the LICENSE file): MIT, "Copyright (c) 2026 Holger Leichsenring".
  • Verified repo facts (GitHub API, Nov 19, 2026): 46 stars, 11 forks, 2 open issues; repo created Feb 16, 2026; last push today, Nov 19, 2026. It is a quieter project than yesterday's LoopForge — small community, solo maintainer (a GOVERNANCE.md and a professional-services partner exist), which is itself a real dependency risk.
  • What it does (simple English): you drop a ticket into Azure DevOps, Jira, GitHub or GitLab. The factory reads it, derives a specification with done-criteria, clones every repo of the project into its own sandbox (a .NET repo gets the .NET image, Node gets node:20, Python gets python:3.12), works the specs in order, runs the verification each repo declares, and opens one pull request per repo, cross-linked, writing the PR URLs back to the ticket. Reasoning lands on disk: specs under .agentsmith/specs/, every choice with the alternative it beat under .agentsmith/decisions/, and per run a result.md with the delivery account, token usage and dollar cost.
  • The verification step: green tests are not the verdict. A separate reader that never saw the work being done goes through each done-criterion: met, unmet, or not applicable, and must cite what on the branch proves it. A run that comes back short still opens its PR as a draft with a section naming what was not delivered, and you can overrule a single verdict with a reason that stays on the record. When a run hits a question it shouldn't answer alone, it checkpoints and waits — days if needed — without burning tokens. A ticket too thin to work from gets asked, not guessed at.
  • More than code: one orchestrator, many pipelines: pr-review (line-anchored review comments), security-scan (a security master reconciled against scanners, each finding required to survive a refuter), api-security-scan (Nuclei, Spectral and ZAP against a live API, judged the same way), legal-analysis, mad-discussion, spec-dialog and a dashboard "Work it out" conversation that drafts tickets with reviewed specs and files them only when you approve.
  • New release status: this is not a previously featured project; today's v0.191.1 is its first full appearance on this radar.
  • Recent verified changes: v0.191.1 released today, Nov 19, 2026 07:08 UTC (fix: a green finish_spec is not re-driven for unbacked done steps); v0.191.0 earlier today (spec-dialog design master owns its draft; secret cards now name the registries whose token uses them); three releases in the last two days. Active.
  • Why it matters to a vibe coder: it is the open-source embodiment of "proven, not trusted" — independent evidence with citations, PRs that never hide a shortfall, decisions logged with their rejected alternatives, and a cost receipt per run. That is the exact accountability a one-person agency owes its clients.
  • Costs (verified status): MIT software, your infrastructure. Real costs: an AI provider API key (Claude, OpenAI, Azure OpenAI, Gemini, Ollama local, or GitHub Copilot seats) and a machine for Docker/Kubernetes if you go server mode. Open source ≠ free model access.
  • Windows compatibility: the README says every platform, including Windows, is on the releases page; verified that Windows assets are claimed there, but not tested on this PC. The agent-smith demo needs only one LLM key — no tracker, no Docker, no Redis.

Honest reading: agent-smith's strongest stages are SPECIFICATION, QA and SECURITY — the three where yesterday's LoopForge was weakest. Its weakest are LEAD, pricing and RELEASE/deployment, which map exactly to what a client agency must still do by hand.

Honest Gaps

  • LEAD: no lead qualification, pricing or client intake; "Work it out" starts from a question you already have. Business development stays outside.
  • PROPOSAL: produces internal specs and cost receipts, not priced, client-facing quotes; you assemble the quote yourself.
  • RELEASE/deployment: the factory ends at pull requests and updated tickets. No build-and-deploy or release-candidate stage; a deployment tool would have to be verified separately (untreated candidate here, not advice).
  • Governance vs. verification: a separate reader with citations is a superb evidence generator, but there is no project-state.json, no lifecycle transition enforcement, and no rollback-across-stages engine. Its verification complements gate_engine.py, never replaces it.
  • Bus factor: a solo maintainer at 46 stars with a commercial services arm; community review is thin compared with trending projects. Read GOVERNANCE.md before relying on it.

Why It Fits Agency OS

  • Evidence before advancing: "green tests aren't the verdict" — advancement listens only to a per-criterion account from a reader that never saw the work being done. That is the closest open-source match found so far to Agency OS's "evidence validated before advancing" rule.
  • Agents never invent facts, approvals or evidence: verdicts must cite what on the branch proves them, not summarize intent; a thin ticket is asked about, not guessed at; decisions are recorded with the alternative they beat. The security master's findings must survive a refuter before delivery.
  • Human approval points: a run stops and waits (token-free) at anything it must not decide alone, and "Work it out" files tickets only on your say-so. Caveat, honestly: it checks with you, but does not enforce a fixed stage-gate ladder — that enforcement remains Agency OS's job.
  • Living project state: the spec, decisions, tickets and per-run accounts are files on disk that stay current — both the repo's and the project's.
  • Specialized agents coordinated by an orchestrator: one orchestrator drives different "masters" (code, pr-review, security, legal) per pipeline; readers are deliberately separated from builders in context.
  • Compatibility status: plausible, untested. Nothing verified shows agent-smith reads project-state.json or enforces Agency OS transitions; its delivery account would enter governance as candidate evidence only.

Limitations, Risks & Human Review

  • Small, young project: 46 stars, one maintainer, three releases in two days (stability is being chased, not proven). Pin releases and read the changelog; don't build client deadlines on it before a trial.
  • Self-reported receipts: the big numbers in the README (1,332 specs done, 6,806 decisions, 10,944 tests, 1 in 6 specs stopped by the commit gate) are maintainer-accounted, not independently audited. Treat directionally.
  • Sandbox trust: containers are toolchain isolation, not hostile-code containment; the same caution as any Docker-based factory. Run it on a machine that doesn't hold your client secrets.
  • Token spend: multi-repo, per-spec pipelines with independent verification can burn real money on its providers; the per-run cost accounting exists precisely so you watch it. Model pricing via Claude/OpenAI/Gemini APIs or subscription seats; Ollama is the free-but-local path.
  • Setup weight: real use wants a tracker, repo auth and one or more provider keys; the zero-tracker demo needs just one LLM key. Kubernetes mode is overkill for a one-person shop; the single binary is the right start.
  • Windows: Windows assets are offered on the releases page per the README, untested here; the Docker path also assumes a functioning Linux-style environment.

Agency OS Integration Proposal: the delivery account as independent QA evidence for the QA and SECURITY gates

  • Problem solved: Agency OS QA today can lean on the implementing agent's own claims about its work. agent-smith's pattern closes that hole: a second agent with fresh context scores every acceptance criterion met/unmet/not-applicable and must cite branch evidence for each — and it also brings a real SECURITY stage (security master + refuter, API scanning) that the Agency OS QA loop can borrow in one step.
  • Workflow improved: QA and SECURITY gate inputs for client repos: run the delivered branch through a citation-backed criterion reader, keep "met with cited evidence / unmet" as the artifact the gate consumes.
  • Lifecycle point: DEVELOPMENT output → QA (criterion reader verdicts with citations) → SECURITY (security-scan pipeline artifacts) → CEO_REVIEW (your recorded overrule/approval stays on record). SPECIFICATION and REUSABLE_COMPONENT also benefit: decided specs stored with the alternatives they beat.
  • Inputs and outputs: an approved spec or accepted branch in; a per-criterion delivery account, refuter-tested security findings and cost receipts out.
  • How results are validated: gate_engine.py treats the delivery account as candidate evidence only; the reader must have no access to the builder's session reasoning; scripts/declared verification stays the deterministic layer; every gate advance still requires human approval. agent-smith never auto-advances an Agency OS gate.
  • What happens on failure: unmet criteria block the gate as candidate-evidence failure; rework goes back through development; lifecycle rollback remains exclusively gate_engine.py's job — the two never overwrite each other.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). Scope changes, client acceptance, release and commercial decisions stay human.
  • Smallest safe experiment: today's one-key demo; if the delivery-account format reads as evidence your QA gate would accept, wire one scratch repo through agent-smith doctor + code --ticket N and compare its criterion verdicts with your current QA sign-off.

Daily Learning: "the separate reader" — the antidote to self-graded science

  • Concept (simple English): agent-smith never lets the agent that did the work declare it done. A second reader, with fresh context and no access to the author's reasoning, walks the done-list one criterion at a time and must cite what on the branch proves each one. Its account, not the builder's summary, is what the verdict listens to.
  • How an AI agent might get it wrong: an agent asked "did you finish?" will say yes — it re-reads its own confident output and ratifies itself. Worse, when one agent writes both the code and the tests, the tests encode the same assumptions as the code and pass even when the behavior is wrong (the oracle problem).
  • How you recognize the failure: done-celebrations that quote the agent's summary rather than artifacts; tests that were written and passed inside the same session as the feature; a review that never cites a file, line or diff; acceptance criteria restated rather than checked.
  • What detects it: split doer from checker, forbid the checker the author's reasoning, and require citations to real artifacts (branch, diff, test output) for every criterion — then let gate_engine.py re-validate that evidence and keep the human as the only gate-advancer.
