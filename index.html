The problem: a one-person agency juggling several client projects ends up running agents in five places: one in an IDE, one in a terminal, one on the laptop, one on a server, one triggered by a GitHub issue. Nothing connects them. Leads arrive in Slack and GitHub and sit there; dependency updates and code review pile up; agents die when the laptop lid closes.

  • What it does (simple English): a self-hosted control center for coding agents. One canvas starts conversations with your agents and runs automations on schedules or webhook events (GitHub, Slack, Linear, Notion integrations). Why It Fits Agency OS

  • One connected factory, not a toolbox: the canvas connects lead intake (GitHub/Slack), agent execution, review automations and maintenance schedules into one always-on surface — exactly the connected end-to-end workflow the radar format asks for.
  • Bring your own agent and model: it does not lock you into one provider; your existing Claude Code/Codex subscriptions and API keys stay valid, and switching agents does not discard session state.
  • Sandboxing by default: the documented "with a Docker Sandbox" mode keeps agent file access inside a mounted workspace — aligned with your scoped-permission rule. (The no-sandbox mode grants full filesystem access and must be avoided.)
  • Event-driven intake: automations respond to real webhook events rather than invented ones — consistent with "agents must never invent facts/approvals/evidence": a run without a triggering event does not exist.
  • Compatibility status: plausible, untested. Nothing in the docs shows it reads project-state.json or enforces lifecycle gates, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • No-sandbox mode is dangerous: the README itself warns that installing without the Docker sandbox gives the agent full filesystem access. Always run the sandboxed mode; keep the mounted workspace separate from sensitive data.
  • No human approval gates: automations run on schedules and webhooks without a human checkpoint. Under Agency OS rules, CEO_REVIEW, scope changes, waivers, client acceptance and release stay in your gate engine — do not wire a release automation directly.
  • Always-on means always-spending: agents that keep running on a server consume model tokens continuously; set per-run limits and monitor usage.
  • Self-hosting security is on you: a cloud/VM installation needs the project's own security-hardening guidance read first, especially if automations are reachable from Slack/GitHub webhooks.
  • Fast cadence: 161 releases; pin the exact version you install (today: v1.38.0).
  • Windows: CI-verified install path exists, but untested on this PC.

Test Today: sandboxed local Agent Canvas on a scratch workspace (~1 hour, Windows PC)

  • Prerequisites: Node.js 24+ and Docker Desktop (for the sandbox), plus one model API key or an existing Claude Code/Codex subscription. Nothing new to buy.
  • Official steps (from the README): follow the Windows PowerShell quickstart, or run the Docker sandbox: docker run -it --rm -p 127.0.0.1:8000:8000 -v openhands-state:/home/openhands/.openhands -v "C:\openhands-projects:/projects" ghcr.io/openhands/agent-canvas:1.38.0, then open http://localhost:8000/canvas.
  • Practical test: create a scratch GitHub repo with one small issue ("add a word-count CLI"), connect the GitHub automation, and watch the issue get decomposed into tasks and picked up by the agent in the sandbox.
  • Expected results: a task decomposition from the issue, code changes confined to the mounted scratch workspace, and a visible automation run log — evidence the lead-to-task-to-code path works end to end.
  • Safety precautions: sandbox mode only; scratch workspace only; bind to 127.0.0.1 (never expose to LAN); pin v1.38.0; read the self-hosting security notes before any server install.

Agency OS Integration Proposal: Agent Canvas as the LEAD/DISCOVERY intake surface

  • Problem solved: leads and issues arriving in GitHub and Slack today wait for you to manually open a session; nothing decomposes them into tasks while you sleep.
  • Workflow improved: the orchestrator's LEAD → DISCOVERY → PROBLEM_DEFINITION entry path — GitHub/Slack events trigger an automation, the issue is decomposed into tasks, output lands in the workspace for the orchestrator.
  • Lifecycle point: LEAD and DISCOVERY, feeding PROBLEM_DEFINITION.
  • Inputs and outputs: a GitHub issue or Slack message in; a task decomposition and workspace changes out, with the automation run log as evidence.
  • How results are validated: gate_engine.py treats the automation's task decomposition as candidate input only; a human confirms the problem definition before the PROBLEM_DEFINITION gate advances. Decompositions without a real triggering event stay UNVERIFIED.
  • What happens on failure: a failed or empty decomposition marks the intake attempt logged-not-advanced; nothing proceeds to PROPOSAL without human-confirmed problem definition. No auto-waivers.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). Human approval still required at CEO_REVIEW, scope changes, waivers, client acceptance and release — Agent Canvas automations are never wired past those gates.
  • Smallest safe experiment: today's scratch-repo test; then compare the issue-decomposition output against what your DISCOVERY stage template expects. Zero changes to Agency OS scripts.

Daily Learning: the unattended-run problem (event-driven automation safety)

  • Concept (simple English): an "always-on" agent is only safe when three things hold: it is sandboxed, it is triggered by real external events, and its output stops at a human gate. Miss any one and you have an agent with keys and no supervision.
  • How an AI agent might get it wrong: it "helpfully" invents a task when no real event arrived, runs on a schedule against the wrong repo, or treats an automation run log as proof the work was correct.
  • How you recognize the failure: automation runs with no corresponding GitHub issue or Slack message; task lists appearing overnight with no client request behind them; run logs presented as evidence.
  • What detects it: trigger-to-run correlation (every run must trace to a real webhook event) plus your gate engine: intake evidence without a verified trigger stays UNVERIFIED and cannot advance past DISCOVERY.
