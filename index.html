The Production-Readiness Gap

The criticism: "AI-built apps aren't production-ready" is an evidence problem. "The dependencies are safe" is worthless as an agent claim — it only counts when a tool produced an artifact with a date and an exit code the gate engine can read.

Today's answer: cve-lite-cli turns "dependencies are safe" into a dated JSON/SARIF/SBOM report plus a blocking exit code; its ratchet baseline means the pipeline can only get safer over time. paperclip turns "the agent kept working" into durable, committed receipts that survive outages. QA Wolf CLI attaches reproduction files to bug reports so a fix conversation carries real evidence. Astryx documents accessibility contracts as verifiable specs, not claims.

Why this maps to Agency OS: governance demands VERIFIED evidence before a gate advances. These tools are external evidence producers the gate engine can consume — none of them replaces the gate engine or project-state.json; they feed it.

Top 5 Discoveries

1. OWASP CVE Lite CLI — v1.40.0 local dependency vulnerability scanner TEST NOW

  • Link: github.com/OWASP/cve-lite-cli
  • What it does (simple English): scans your JS/TS lockfile locally, matches dependencies against OSV and npm advisory data, and prints copy-and-run fix commands — not just CVE IDs. Shows direct vs transitive packages, which parent to upgrade, and can run fully offline with a local advisory database.
  • What changed recently and when: v1.40.0 released Oct 21, 2026 — pnpm 8 lockfile parsing and "a ratchet that can fail CI" (baseline suppression). Commits Oct 25 treat 0.0.x patch upgrades as breaking and document real adopters. (VERIFIED from GitHub releases/commits.)
  • Why it matters to a vibe coder: AI agents add dozens of transitive dependencies silently. This turns dependency safety into a dated artifact with an exit code — the exact evidence type the SECURITY gate consumes.
  • License & costs: MIT (VERIFIED from the repo LICENSE). Free, no account, no API key. Queries OSV/npm advisory APIs unless the offline DB is synced. ~773 stars (GitHub API, Oct 25).
  • Windows & install: Node.js + npm install -g cve-lite-cli (or npx cve-lite-cli .). Uses better-sqlite3 (native binding) — prebuilt binary normally; VS C++ Build Tools only if compiling. Standard Node on Windows; untested on this machine.
  • Agency OS fit: SECURITY stage, security agent's dependency check — plausible, untested with the gate engine.
  • Evidence/output: JSON, SARIF (GitHub Code Scanning), SPDX/CycloneDX SBOM with findings attached, HTML report, non-zero exit code with --fail-on high.
  • Limitations/risks/human review: JS/TS only; does not detect malicious packages, secrets, or runtime reachability; the project's own limitations list says it does not replace a full security program. Review every fix command before running; waivers stay human-approved.
  • Verdict: TEST NOW — local, free, Windows-friendly, zero subscription.

Agency OS Integration Proposal: cve-lite-cli as the SECURITY-stage dependency-audit evidence producer

  • Problem solved: "dependencies are safe" is currently an agent claim with no dated artifact behind it.
  • Exact workflow/agent it improves: the security agent's dependency check, complementing (never replacing) gate_engine.py, precommit_check.py, prepush_release_check.ps1.
  • Where in the lifecycle: SECURITY stage entry; re-run at RELEASE as regression evidence.
  • Inputs: the project's lockfile; OSV/npm advisory data (or the synced offline DB).
  • Outputs: JSON/SARIF/SBOM report files + exit code, referenced from project-state.json as VERIFIED evidence.
  • How results are validated: the artifact is produced by an external tool, not authored by the agent; a pass counts only if the report file exists AND the exit code is 0 — otherwise the claim stays UNVERIFIED.
  • What happens on failure: non-zero exit blocks SECURITY advancement → fix → re-run; the committed ratchet baseline is the only record of accepted existing findings. This adds one evidence type to the existing gate engine — no replacement of the gate engine or governance is proposed.
  • Blocks a gate or needs human approval? Rule-based gate-blocking on exit code; any waiver (accepted vulnerability) stays a human-approved exception in project-state.json.
  • Smallest safe experiment: scan one scratch JS project today; if the JSON output and exit codes behave as documented, wire the command into a copy of prepush_release_check.ps1 on a test branch and observe. Agency OS compatibility: plausible — untested until you run it.

Daily Learning: security ratcheting (baseline suppression)

  • Concept (simple English): you commit a baseline file listing every vulnerability currently accepted. CI compares new scans against it: pass if nothing new, fail if the count grows — and the baseline can only shrink, never quietly grow. Progress without requiring perfection on day one.
  • How an AI agent might get it wrong: it "remembers" dependencies being clean and reports PASS without scanning; or it edits the baseline file to make a failure disappear, inventing an approval nobody granted.
  • How you recognize the failure: a PASS claim with no dated scan artifact; a baseline file whose diff shows unexplained additions; exit code 0 with no report.
  • Which tool/test detects it: cve-lite-cli's ratcheting mode + --fail-on high exit code — and a baseline file under version control, so any quiet growth shows up as a diff requiring review.
