Start Here (plain English)

The problem: most coding agents are fast but unaccountable. They answer, they edit, they claim success — and nothing forces them to prove it. A solo agency shipping to real clients does not need a faster guesser; it needs a factory whose process is written down, whose checks actually run, and which stops and asks a human before doing something that matters.

The solution in today's radar: bastani-inc/atomic, the "verifiable coding agent runtime". You define your engineering process as explicit, checkable execution graphs: skills describe procedures, executable checks prove they worked, subagents do scoped work in isolated git worktrees, and human approvals are first-class stops in the run. It is the first entry in this radar whose core pitch is not speed but evidence — the same value Agency OS's gate engine enforces.

The Featured Factory: bastani-inc/atomic — the verifiable coding agent runtime TEST NOW

  • Link: github.com/bastani-inc/atomic — TypeScript; a fork of Pi, so it works with existing Pi providers, tools, MCP servers, skills and extensions.
  • License (verified from the LICENSE file, Nov 26, 2026): MIT (Copyright 2025 Bastani, Inc.) with one unusual clause: products exceeding 100 million monthly active users or $20 million monthly revenue must prominently display "Atomic" in the UI. For a one-person agency this clause is irrelevant; for anything you white-label at scale, it is not.
  • Verified repo facts: 883 stars, first published Oct 23, 2025, commits today (Nov 26, 2026: e217114, preparing 0.10.11-alpha.2, plus a storage-forks feature earlier the same day). Latest release: 0.10.10, published Nov 25, 2026, with signed SHA256SUMS and binaries for macOS (x64/arm64), Linux (glibc and musl) and Windows (x64 and arm64 zips).
  • What it is (simple English): a coding-agent runtime where you build the process, not just the prompt. A skill describes the procedure; the parent chat uses codemode to call tools, launch specialist subagents, and decide the next step from an actual check result. Complex runs "can take hours, days, or weeks because Atomic researches, implements, and verifies the work that quick coding-agent passes tend to leave to you." Nine bundled subagents (worker, codebase-locator, codebase-analyzer, pattern-finder, online-researcher, research-locator, research-analyzer, code-simplifier, debugger) do scoped work; parallel agents each get their own git worktree; sessions persist to SQLite or greppable JSONL and can fork, branch and resume on another machine via blueprints (.atomic/blueprint.yaml).
  • Classification vs yesterday: an update, not a new project — the repo dates to Oct 2025, and release 0.10.10 (Nov 25, 2026) added live compaction/decision-model switching, a typed CompactionError SDK family, and PostgreSQL/libSQL shared storage for cross-machine sessions and Intercom.
  • Human-in-the-loop by design: ask_user_question stops a run mid-task with a structured question UI; a delegate hitting a real product decision "stops, asks the human supervising the run, and waits"; a permission-gate extension catches risky shell calls before execution and asks the operator to allow or block.
  • Why it matters to a vibe coder: it is the first runtime featured here where "no advance without evidence" is the execution model, not a bolted-on checklist — the FAQ even says to put deterministic checks in scripts and inspect their exit status before trusting an answer.
  • Costs (real): the software is MIT and free. Model access is not: you sign in with a provider subscription (Claude Pro/Max, ChatGPT Plus/Pro, GitHub Copilot, Kimi Code, OpenRouter, xAI) or API keys; optional remote compaction uses the paid Morph service or your own endpoint; PostgreSQL 16+ or Turso hosting is your cost if you use shared storage. README case-study numbers (95% merge rate, 0% reverts) are vendor-reported, not independently verified.
  • Windows compatibility (verified): explicit Windows support — a PowerShell installer (install.ps1), a Windows docs page, and Windows x64/arm64 release assets. Requires Node.js 24.20+ for the npm install path (the release-archive path needs no Node at all).

Honest Gaps

  • PROPOSAL and pricing: absent, by design. Keep commercial work in Agency OS.
  • RELEASE/deployment: absent. Atomic verifies; it does not ship. Staging, releases and client acceptance stay yours.
  • No sandbox, stated bluntly: the README's own security warning says Atomic "has no built-in sandbox or command-level shell permission gate. Tools and extensions run with your user permissions" and tells you to run autonomous work in a devcontainer, VM or remote machine. This is the biggest operational gap — and the honest part is that they disclose it.
  • Product-level security scanning: the permission hooks guard the factory's reach, not your product code: no SAST, secrets or dependency scanning stage exists. (External filler, if verified separately: a scanner such as Semgrep could slot into the QA/SECURITY boundary — compatibility untested.)
  • No proactive monitoring: nothing watches a released product; MAINTENANCE continuity is about resuming sessions, not about CI babysitting like yesterday's Robin.
  • Governance: approval points and permission hooks exist, but there is no multistage gate engine or living project-state file. Atomic encodes your process; it does not enforce Agency OS's lifecycle. It complements gate_engine.py, it must never replace it.
  • Self-reported metrics: the "95% merge rate / 0% revert rate" figures come from the vendor's README, not from independent audit — treat as marketing until you measure your own runs.

Why It Fits Agency OS

  • Evidence before advancing, as the execution model: the parent agent "decides the next step from an actual check", and the FAQ insists deterministic checks live in scripts whose exit status you inspect — not in the model's opinion of its own work. That is Agency OS's "evidence validated before advancing" rule, implemented in a different codebase.
  • Human approval as a primitive: ask_user_question mid-task, supervisor escalation that "stops... and waits", and permission-gate hooks that ask before risky calls. Approval is a control-flow stop, not a suggestion.
  • No invented facts by construction: specs must be "grounded in research and engineer feedback"; research subagents return file paths the parent reads and verifies; children return results the parent checks. The architecture assumes children may be wrong.
  • Living state as greppable files: todos under .atomic/todos/, specs under specs/, sessions as append-only JSONL "you can grep, diff, and script against" — the same spirit as project-state.json, though not the same format or authority.
  • Specialized agents coordinated, not a monolith: nine scoped subagents with defined termination conditions, planner-worker Intercom coordination, and worktree isolation so parallel work cannot collide — structurally the closest match to Agency OS's specialized-agents-plus-orchestrator model seen in this radar so far.
  • Compatibility status: plausible, untested. Nothing indicates Atomic reads project-state.json or speaks Agency OS gates; its artifacts (specs, research docs, check results, escalation records) enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • The no-sandbox warning is the headline risk: tools run with your user permissions. Until it sits in a devcontainer or VM, do not let it run unattended anywhere near client code, SSH keys or browser sessions.
  • Runs are deliberately slow: "complex runs can take hours, days, or weeks." Budget token cost accordingly — a verification-heavy run on a paid subscription or API keys is a real invoice, and the repo publishes no cost estimates.
  • Fast-churning releases: 0.10.x with alpha builds already in prep (0.10.11-alpha.2) and documented breaking changes in 0.10.10 (required CompactorRequest.baseUrl, removed KnownCompactorApi). Pin versions; the vendor's own pattern says breaking changes are routine.
  • License clause to remember: MIT, but >100M MAU or >$20M monthly revenue products must display "Atomic" in their UI. Harmless for Agency OS today; note it in REUSABLE_COMPONENT if you ever build on the SDK for a scaled product.
  • Windows is supported but new territory: installers and docs exist (verified), but the radar has not tested a Windows run; PowerShell install plus Node.js 24.20+ is the documented path. Fork: the @bastani/atomic-natives native module has per-platform binaries, with a documented Android/Termux build path only via package manager.
  • Human review points: what tasks you hand it (LEAD), every supervisor escalation answer (it will act on whatever you reply), every permission-gate prompt, and every merge on a client repository. Never delegate those.

Test Today: a 45-minute Windows-friendly, scratch-repo-only evaluation

  • Zero-cost first pass (10 min): in a scratch repository (never a client repo), install with npm install -g @bastani/atomic (Node.js 24.20+ required) or the PowerShell release-archive installer, and run atomic. Confirm your cheapest provider login works before anything else.
  • Verifiability pass (20 min): ask it to produce a spec with create-spec for a trivial feature, then implement it with a worker subagent and a scripted check that must pass before it stops. Inspect: does specs/ contain a real file? Did the check actually run? Try a deliberately failing check and confirm the repair loop respects its bound instead of re-running forever.
  • Governance pass (10 min): test ask_user_question mid-task and a permission-gate hook on a risky command. The question is whether the run genuinely stops and waits — the property Agency OS's gate engine needs from any executor.
  • Expected results: evidence files on disk (spec, todos, JSONL session), one verified escalation, and one verified bounded-repair stop — the three behaviors that decide whether Atomic can serve as an Agency OS DEVELOPMENT/QA executor.
  • Safety precautions: scratch repository only, no client credentials in the environment, ideally inside WSL2 or a devcontainer given the no-sandbox warning; keep a token-cost note as you go.

Agency OS Integration Proposal: Atomic as the DEVELOPMENT/QA executor, with checks promoted to gate evidence

  • Problem solved: Agency OS's QA gate is only as strong as the evidence feeding it. Atomic's distinctive verified capability is executable checks with bounded repair loops — the run cannot claim done until the script's exit status says so.
  • Workflow improved: inside DEVELOPMENT, run the implementation as an Atomic session in a devcontainer worktree: spec from specs/ in, worker subagents implement, scripted checks must pass within a bounded repair count, and any product decision escalates and waits. The gate engine sees the check exit statuses and artifacts as QA evidence.
  • Lifecycle point: DEVELOPMENT and QA only. LEAD, DISCOVERY, PROPOSAL, SPECIFICATION sign-off, SECURITY, CEO_REVIEW, RELEASE and governance stay untouched; gate_engine.py, project-state.json and human approvals are unchanged.
  • How results are validated: every check is a deterministic script whose exit status and artifacts the gate engine inspects before advancing — an agent's "done" claim carries no weight, exactly as Agency OS requires. Escalation answers are recorded in the session JSONL as reviewable evidence.
  • What happens on failure: the bounded repair loop exhausts, the run stops with the failing evidence attached, and the gate refuses to advance — the failure surfaces as a blocked QA gate, not a silently merged guess.
  • Smallest safe experiment: one scratch repo, one feature, one scripted check, token cost logged. Promote to a client project only after the escalation and bounded-stop behaviors reproduce reliably. Compatibility plausible/untested.

Daily Learning: "the run stops at the check" — bounded repair loops

  • Concept (simple English): an unbounded agent retries forever, burning tokens until failure starts to look like success. Atomic's orchestration patterns pair every verification with a bounded repair loop: "stop when it returns 429 with Retry-After or after three repair attempts." The stop condition is written before the run, in plain language, and it names what counts as done.
  • How an AI agent might get it wrong: a repair loop with no bound "fixes" a failing test by weakening the test, or retries until a flaky pass lets it declare victory. The agent reports success honestly — its definition of success was wrong from the start.
  • How you recognize the failure: sessions with repair counts far above the plan; diffs that touch tests in the same commit as the "fix"; a green final check that followed N retries with no recorded diagnosis between them.
  • What detects it: declare the bound and the success criterion in the task definition before the run (as Atomic's examples do), record each repair attempt with its evidence, and let gate_engine.py refuse any QA evidence whose repair count exceeded the declared bound without a human note. In Agency OS terms: a stop condition you did not write in advance is not a stop condition, it is a hope.
