Start Here (plain English)

The problem: a vibe coder faces a trap. Either you babysit every agent step, or you walk away and get a 50-file diff you don't trust. Both kill a one-person agency's throughput: the first consumes your day, the second burns your credibility with the client.

The solution in today's radar: fabro-sh/fabro, the open source "dark software factory for expert engineers." You define your delivery pipeline as an explicit, reviewable graph (plan → approve → implement → verify, with branches, loops and human gates), the engine executes it with AI coding agents, every stage is checkpointed to git, and failures in verification trigger automatic fix loops. You intervene only where judgment matters.

The Featured Factory: Fabro TEST NOW

  • Link: github.com/fabro-sh/fabro · docs: docs.fabro.sh
  • License (verified from the repo's license page): MIT.
  • Verified repo facts (GitHub, Nov 9, 2026): ~1.8k stars, 201 forks, 36 contributors, 5,635 commits, 159 releases; latest stable release v0.254.0 (Jun 4, 2026); latest commit Nov 5, 2026 ("Bump version to 0.408.0-nightly.0"). This is an update to an established, fast-moving project, not a new project.
  • What it does (simple English): a workflow orchestration engine. You write your software process as a Graphviz DOT graph with human approval gates; Fabro executes it with AI coding agents (Claude Code, Codex and others, routed via CSS-like model stylesheets), commits each stage to git, and gives you a local server, REST API with SSE events, and a React web UI showing every run.
  • Key verified features (from the README): deterministic workflow graphs; human-in-the-loop approval gates, mid-run steering and interview steps; multi-model routing with fallback chains; cloud sandboxes (Daytona) with network isolation; git checkpointing per stage (resume, revert, trace); automatic retrospectives with cost, duration and files touched; a single Rust binary with no Python, Node or Docker required.
  • What changed recently (verified): latest commit Nov 5, 2026 (nightly 0.408.0); the repo has shipped 159 releases with nightly cadence, so expect churn — pin your install.
  • Why it matters to a vibe coder: it is the closest verified open-source analogue to Agency OS's core idea — deterministic process, agents as executors, human approval points, evidence at every step — without renting a platform.
  • Costs (verified status): the software is free (MIT). Real costs are your model provider APIs (Claude Code / Codex subscriptions or tokens). Optional cloud sandboxing uses Daytona, an external cloud service whose pricing is unverified here. Open source ≠ free model access or free cloud.
  • Windows compatibility (verified from official docs): native Windows is NOT supported. The official Quick Start lists Windows as unsupported and directs you to WSL2 with a supported Linux architecture. Windows status: UNTESTED native, WSL2 route documented by the project.

Why It Fits Agency OS

  • Process as code: the workflow graph is diffable, reviewable and version-controlled, the same philosophy as gate_engine.py — the graph, not the agent, owns control flow.
  • Human gates: approval gates pause for human decisions, matching your CEO_REVIEW rule that humans approve scope and commercial decisions.
  • Evidence at every step: per-stage git checkpoints and durable run events give the trail your "evidence must be validated before advancing" rule needs.
  • Honest cost data: automatic retros report real cost and duration per run, evidence you can attach to project-state instead of guessing.
  • Compatibility status: plausible, untested. It complements the gate engine and never replaces it; no evidence yet that it reads project-state.json.

Limitations, Risks & Human Review

  • "Dark factory" unattended runs are the selling point and the risk: an unattended agent in a fix loop can churn tokens and produce many commits. Keep client code out until you trust the workflow.
  • Nightly release cadence means churn; pin the version you install.
  • Native Windows unsupported: everything runs inside WSL2 on a Windows PC, which conveniently keeps untrusted code off Windows proper. Do not enable cloud sandboxes for the first test.
  • Cloud sandboxes (Daytona) are an external service; pricing unverified here.
  • Human review required at every approval gate and before merging any checkpoint branch; never grant unrestricted computer access; read the DOT graph before running it.

Agency OS Integration Proposal: Fabro's graph engine for the DEVELOPMENT → QA fix loop

  • Problem solved: the orchestrator currently relies on prompts to keep the dev → QA loop disciplined; nothing deterministically enforces the loop or records per-stage evidence.
  • Workflow improved: the orchestrator's DEVELOPMENT → QA loop, run by the dev and QA agents.
  • Lifecycle point: DEVELOPMENT and QA, with human gates feeding CEO_REVIEW.
  • Inputs and outputs: a spec from SPECIFICATION plus a DOT workflow in; git checkpoint branches, per-run durable events, pass/fail verification evidence and retros out.
  • How results are validated: gate_engine.py consumes verification-node results and git checkpoints as evidence before the SECURITY transition; runs without validated evidence stay UNVERIFIED.
  • What happens on failure: the fix loop runs inside Fabro; if retries exhaust, the stage is BLOCKED and returns to the dev agent. Nothing auto-waives.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). Human approval still required at plan gates, scope changes and release.
  • Smallest safe experiment: today's WSL2 scratch test, then compare Fabro's event and checkpoint outputs against what precommit_check.py expects as evidence. Zero changes to Agency OS scripts.

Daily Learning: process as code ("the graph, not the agent, owns control flow")

  • Concept (simple English): the workflow graph defines what happens next; agents only execute nodes inside it. Control flow becomes reviewable source code instead of an agent's judgment.
  • How an AI agent might get it wrong: it improvises "helpful" steps outside the graph — writing code during a plan node, skipping a verification step, or committing outside the checkpoint pattern.
  • How you recognize the failure: stage outputs are missing or out of order, or git history shows commits that don't match the stage checkpoints.
  • What detects it: Fabro's durable run events plus git checkpoint inspection; under Agency OS rules, the gate engine rejects any transition whose expected artifact is absent.
