Daily open-source discoveries for a one-person AI software agency

Start Here (plain English)

The problem: AI agents can generate a whole product in an afternoon, but what separates a demo from a client deliverable is everything around the code: a plan someone approved, specs with acceptance criteria, honest review of what was actually built, and proof each requirement is met before it ships. Most agent setups bolt these on afterwards, if at all.

The solution in today's radar: safuente/saaf-software-factory, an open-source software factory built entirely from Claude Code agents plus a formal set of human gates. A project brief goes in; the factory plans it into features, writes specs you approve, builds each feature test-first in its own isolated worktree, runs four parallel reviewers plus independent verification against the running app, and opens a pull request only when a human confirms. Agents do the work between stages; humans own every gate.

One featured item per day, per the format confirmed Nov 5, 2026 (re-confirmed Nov 10, 2026). Repo facts, LICENSE and commits verified directly from GitHub on Nov 20, 2026. The Featured Factory: safuente/saaf-software-factory — brief in, spec, TDD build, four reviews, verified approval, pull request out TEST NOW

  • Link: github.com/safuente/saaf-software-factory — a factory expressed as Claude Code agents (one markdown file per agent under .claude/agents/), templates and policies, orchestrated by a /factory command. Not a runtime to install: a factory you clone, read and rewrite.
  • License (verified from the LICENSE file): MIT, "Copyright (c) 2026 Santiago Alvarez".
  • Verified repo facts (GitHub, Nov 20, 2026): repo created November 3, 2026, one author, very small community footprint so far. A young project — a working blueprint, not a crowd-tested product.
  • What it does (simple English): you write a brief.md. The Planner interviews you in questions.md and refuses to plan until you answer. Each feature then runs its own pipeline: a Spec Writer drafts acceptance criteria you approve, a Builder works test-first (failing test committed before the code that passes it, with the order checked from the git log), the orchestrator runs make check and make e2e, then four reviewers (security, code, UX, UI) examine the diff and the running app in parallel. A finding blocks only with a concrete, checkable evidence trail. After at most three fix rounds, an Approver independently re-verifies every acceptance criterion against the running app before a human confirms push and merges the pull request.
  • States in files, not memory: one git worktree, branch, ports, containers and database per feature, so parallel features never touch each other. All state lives in files; any run can be stopped and resumed.
  • Verified recent change (last 7 days): commits November 16 (a budgeted, no-push autonomous mode with a Scout/Validator idea-validation flow and a token usage ledger for every agent run), November 18 (the first end-to-end pilot run recorded — the "Lesson Ledger" example project with specs, builds, reviews, approvals and pilot fixes, including staging checks that every findings file names the current round and head SHA) and November 19 (pilot features up to F08). The README status section still says "nothing has been run end to end yet"; the Nov 18–19 commits show a pilot has since been recorded, so the README lags the pilot.
  • Why it matters to a vibe coder: it is the closest open-source embodiment of the Agency OS idea found on this radar so far — a visible gate ladder with named human approvals, read-only reviewers, evidence required before anything blocks, independent verification against the running app, and per-run token accounting. And it is transparent: every prompt is a readable file you can rewrite to your standards.
  • Costs (real): MIT and free software. Real costs: a Claude subscription or API access (the pipeline leans on Opus for planning, specs, security review and approval, so long runs are not cheap), plus Docker, Node, Python tooling, Playwright browsers and ffmpeg locally. Optional ElevenLabs key only for voice-over demo videos. No hosting required; everything runs locally.
  • Windows compatibility: untested here. Claude Code runs on Windows and the factory is mostly prompts plus git worktrees, but it also expects make, Docker and a POSIX-flavoured shell; the README does not claim Windows support either way. The realistic Windows path is WSL2.

Honest Gaps

  • PROPOSAL and pricing: no client quote, proposal or commercial layer; the factory starts from a brief the owner already wrote.
  • RELEASE/deployment: the author states plainly, under "Status and what is missing", that the pipeline ends at the pull request and that deployment, monitoring and incident handling are future work.
  • Enforcement is prompt-level: agent boundaries ("no push", "reviewers read-only") live in prompts and recommended .claude/settings.json deny rules, not yet in code; the author lists a code-enforced orchestrator as pending work. Prompts are advisory, not deterministic.
  • Not end-to-end proven: the README says nothing has been run end to end; the Nov 18–19 pilot commits begin to close that gap, but it is one project, one stack, by the author who wrote the prompts.
  • Single-provider dependency: everything routes through Claude Code; there is no second-model reviewer to reduce shared blind spots (the author flags this as a future item).
  • Governance: no project-state.json, no lifecycle transition enforcement, no rollback. Its gates complement gate_engine.py, never replace it.
  • Biggest gap for a client-facing vibe coder: no release/deploy stage, and no lead/pricing layer — both stay manual in Agency OS.

Why It Fits Agency OS

  • Named human gates, not checkbox culture: a dedicated human-gates table names exactly what a person checks before anything advances — plan, spec, escalations, push, merge — as visible, auditable file artifacts.
  • Evidence before advancing: reviewers can only block with findings that name a concrete, checkable consequence; the Approver validates every acceptance criterion against the running app instead of trusting the Builder's own tests.
  • Agents never invent facts, approvals or evidence: TDD order is checked from the git log; reviewer findings files must carry the current round and head SHA (added in the Nov 18 pilot fixes); the launch kit explicitly forbids invented testimonials, user counts or statistics, and the autonomous mode writes a final report listing every decision it took without a human.
  • Specialized agents coordinated by an orchestrator: one /factory orchestrator dispatches narrow agents (planner, spec-writer, builder, security/code/UX/UI reviewers, approver, demo-recorder, landing-writer) — the same separation Agency OS assumes.
  • Living project state: plan, specs, builds, reviews, approvals, budgets and usage logs are files on disk per project that any run can stop, resume and audit.
  • Compatibility status: plausible, untested. Nothing shows saaf reads project-state.json or enforces Agency OS transitions; its artifacts would enter Agency OS governance as candidate evidence only, validated before any gate advance.

Limitations, Risks & Human Review

  • Young, barely-proven project: created Nov 3, 2026, single author, near-zero community. No issue history to learn from, no external audit, no Windows report. Do not anchor client deadlines to it before a trial.
  • Windows: requires make, Docker and a POSIX-style shell; treat WSL2 as the realistic Windows path. Untested on Windows here — verify before promising anything.
  • Token and subscription cost: the pipeline is Opus-heavy at planning, spec and approval. The usage ledger shows the spend but does not cap it in normal mode; budget before long runs or /factory auto.
  • Unattended-run safety: /factory auto is capped by hard budgets (features, ideas, agent launches) and is local-only (no push, no remote, no external services), but its guardrails are prompts plus recommended settings denies, not code. Install the suggested .claude/settings.json denies (force-push, hard reset, unsupervised gh) before any real run.
  • Human review points, honestly: the gates are real, but nothing structurally stops a misfiring agent from editing files outside its worktree if permission rules are not configured; reviewers only stay read-only by prompt and settings discipline.

Agency OS Integration Proposal: a human decision record for the QA gate (not a new engine)

  • Problem solved: today the story of what a human approved and why often lives in chat scrollback, not next to the artifact. saaf makes each human gate a written, auditable file: what the decision was, what was asked, what was explicitly checked — the Approver even lists "Decision" reasoning on every run.
  • Workflow improved: the SECURITY → CEO_REVIEW handoff and the QA gate: attach a short decision record (markdown) per gate input so the gate's evidence includes the human's stated rationale, not just a pass/fail flag.
  • Lifecycle point: QA and CEO_REVIEW gate artifacts, and any handoff where a human signs off. The decision record rides beside the evidence, never instead of it.
  • Inputs and outputs: a completed gate input (e.g., security-check-report.md) in; a decision record naming the human, the date, the checks performed and the explicit approval or objection out, stored next to the artifact.
  • How results are validated: gate_engine.py still validates the artifact and enforces the transition; the decision record is evidence attached to it, not a bypass. No governance, gate engine or project-state.json logic changes.
  • What happens on failure: if pass evidence is missing, nothing new happens — the existing gate already blocks. The decision record only lights up on real transitions, so there is no new failure mode.
  • Gate or human approval: the decision record strengthens human-approval traceability but never replaces the human, and never advances a gate by itself.
  • Smallest safe experiment: on today's scratch project, manually write one saaf-style decision record after approving its spec; if gate_engine.py reads it cleanly and the audit trail reads better than chat scrollback, template it. If not, discard — no code was changed.

Daily Learning: prompt-level governance vs. code-level governance

  • Concept (simple English): saaf enforces its rules in two places. Some rules are prompts inside agent definition files ("reviewers are read-only", "block only with checkable evidence"). Some are settings-file deny rules (git push --force, git reset --hard). Prompt rules are easy to write and easy for an LLM to ignore under pressure; code and config rules are harder to write and much harder to bypass. A mature factory needs both, and its most safety-critical rules belong at the code level.
  • How an AI agent might get it wrong: under a confusing spec, an agent can "helpfully" run a rule it was told not to — normally a read-only reviewer quietly edits a file, or the builder force-pushes over history because the prompt's exception list had an edge case. Prompt boundaries hold only as long as the model keeps recalling them.
  • How you recognize the failure: a transcript claims an agent "followed the rules" while a diff, a push or a merged PR exists that a prompt-only rule should have prevented — the tell that enforcement lived in prose, not in config or code.
  • What detects it: put every rule that must not break into a mechanism the model cannot talk its way past (settings deny rules, CI checks, gate_engine.py); keep prompts for judgement, never for enforcement; diff-audit agent output against declared rules after runs.
