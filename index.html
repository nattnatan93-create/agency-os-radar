Start Here (plain English)

The problem: when you wire several AI coding agents together yourself, three things break. First, nobody records what each agent decided, so a crashed run is unrecoverable and unauditable. Second, agents act on consequential tools (bash, file writes) with nobody approving the risky ones. Third, when something goes wrong you have no verifiable record of what the model actually saw, so you cannot prove your work to a client.

The solution in today's radar: OMA (Open Multi-Agent), an MIT-licensed, self-hosted TypeScript agent runtime built around three verbs: own it, approve it, audit it. Durable approval gates suspend risky decisions until a human answers, an append-only run journal records every adapter call so a finished run can be cold-verified offline, and checkpoints let a crashed run resume instead of restarting. No telemetry, no hosted control plane, your keys and models.

The Featured Factory: OMA — Open Multi-Agent (Self-Hosted Governed Agent Runtime) TEST NOW

  • Link: github.com/open-multi-agent/open-multi-agent · npm: @open-multi-agent/core, maintained by YuanASI (Shenzhen YuanASI Technology Co., Ltd.).
  • License (verified from the LICENSE file): MIT, "Copyright (c) Shenzhen YuanASI Technology Co., Ltd. and open-multi-agent contributors".
  • Verified repo facts (GitHub, Nov 14, 2026): 625 commits, 34 tags; latest commit Nov 13, 2026 (release-bot fix #676). Star count was not independently verified in this check, so none is quoted.
  • What it does (simple English): a Node.js runtime you install into your own backend (npm install @open-multi-agent/core, or scaffold with npm create oma-app@latest, which ships a demo that needs no API key). Three run modes: runAgent() for one agent, runTasks() for an explicit pipeline, and runTeam(), where a coordinator model decomposes your goal into a task DAG and a deterministic scheduler executes it across role-based agents with shared memory. Around that sit the governance features: durable approval gates (plan, task-dispatch, and per-tool-call decisions suspend until approved, and tampered or stale approval state fails closed), a token and cost budget that stops runaway runs, per-agent filesystem sandboxing and scoped credentials, an opt-in egress policy that can confine LLM traffic to an allowlist, consensus verification with independent judges, and an offline Run Viewer that replays a run's task DAG, spans and per-task evidence with no hosted service.
  • Recent verified change: core v1.24.0 released Nov 13, 2026 (yesterday): an NVIDIA NIM provider, experimental image tool, abort now cancels a pending tool approval gate instead of waiting, and journal draining continues after an append failure. This is a new release of an established project (launched April 2026), not a new project.
  • Why it matters to a vibe coder: it is not another agent framework that trusts the model; it is the audit-and-approval layer missing from most of them. Approval gates that fail closed, a verifiable run journal, cost budgets, sandboxed file tools and default-deny tool grants map almost one-to-one onto Agency OS's "evidence before advancing" rule.
  • Costs (verified status): the software is free (MIT). Real costs: one LLM API key (OpenAI, Anthropic, DeepSeek, MiniMax, local Ollama/vLLM and more are supported), plus PostgreSQL if you want production-grade checkpoint stores. Open source ≠ free model access.
  • Windows compatibility: Node.js 20+ required (22 or 24 LTS recommended); the v1.10.0 changelog explicitly fixed killing the full process tree on bash timeouts on Windows and states the test suite passes on Windows. Status: plausible and actively maintained for Windows, UNTESTED on this PC.

Honest Gaps

  • RELEASE/deployment: the pipeline ends at task outputs and reports; nothing builds, versions or deploys. Uncovered.
  • PROPOSAL / client artifacts: nothing generates PRDs, proposals, quotes or client-facing documents; planning artifacts are internal task graphs.
  • ARCHITECTURE documents: the DAG and routing decisions are structure, not an architecture artifact a human can review as a document.
  • SECURITY (code-level): OMA secures the runtime (sandbox, egress, redaction) but does not scan generated code for vulnerabilities. A dedicated scanner such as Semgrep is the classic gap-filler; treat as a candidate to verify separately, not as verified advice.
  • Governance: no project-state file, no lifecycle transition enforcement, no rollback engine. Its approval gates and journals are the raw material for gate evidence, not the gates themselves.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: a coordinator model decomposes goals into a task DAG executed by role-specific agents — the same orchestrator-plus-specialists shape, with a deterministic scheduler rather than agent self-coordination.
  • Agents must never invent facts or approvals: durable approval gates suspend consequential decisions until a human answers; tampered, stale or missing approval state fails closed, and aborting a run cancels a pending gate rather than letting it decide later.
  • Evidence validated before advancing: the append-only run journal records every adapter call, and verifyRun() cold-verifies that a finished run's model-visible content is reproducible from the events it names — a literal implementation of "evidence before advancing".
  • Human approval points: plan, task-dispatch and tool-call approvals are native hooks, and plan patches (mid-run scope changes) can be routed through an onPlanPatch approval — directly aligned with Agency OS's rule that scope changes stay human.
  • Living state: checkpoint/resume with a leased, fenced run store is the runtime equivalent of an authoritative state file that only one worker may advance.
  • Compatibility status: plausible, untested. Nothing in the docs shows OMA reads project-state.json or enforces Agency OS lifecycle transitions, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • Fast-moving minor releases with breaking changes: v1.23.0 (Oct 30, 2026) made zod a required peer dependency, retyped gate schemas, and capped coordinator plans; v1.14.0 raised the Node floor to 20. Pin an exact core version and read the changelog's Compatibility sections before upgrading.
  • It is a library, not an app: you get a TypeScript runtime and CLI, not a finished product; expect to write glue code and configure providers yourself.
  • bash is not sandboxed: the per-agent sandbox covers file tools only; the changelog itself says the bash risk classifier is "explicitly not a security boundary". Keep agents pointed at scratch workspaces and gate bash calls through onToolCall.
  • Historical CVE worth knowing: v1.21.3 fixed file_write escaping the working directory via a dangling symlink (GHSA-h42w-g3ch-rjjm / CVE-2026-108600, affecting 1.5.0–1.21.2). Run 1.21.3 or newer.
  • Costs are real: consensus judges, coordinator passes and retries all consume tokens; use the token and cost budgets (maxCostBudget, token budgets) on any unattended run.
  • Corporate maintainer: MIT terms are unchanged, but the project is maintained by a company (YuanASI) that also sells services built on it — fine today, but watch for feature gravity toward their offering.
  • Windows: Node 20+ (22/24 LTS recommended); the test suite is reported passing on Windows since v1.10.0, but untested on this PC.

Agency OS Integration Proposal: OMA's run journal and approval gates as evidence generators behind gate_engine.py

  • Problem solved: Agency OS agents currently produce evidence you must trust at face value; OMA produces cryptographically replayable run journals and durable approval records, so gate evidence becomes verifiable rather than asserted.
  • Workflow improved: after a gate passes, run the DEVELOPMENT-stage agent work inside an OMA runTeam() with tool gates and budgets; export the run journal, approval ledger and judge verdicts as candidate gate evidence.
  • Lifecycle point: DEVELOPMENT execution plus CEO_REVIEW (durable approval gates) and MAINTENANCE (verifiable journals, checkpoint/resume).
  • Inputs and outputs: an approved task description in; a verified run journal, approval ledger, judge verdicts and task outputs out.
  • How results are validated: gate_engine.py treats OMA journals and approval records as candidate evidence only; QA evidence still comes from your own test runs, and a human confirms before any gate advances. An OMA "success" status is never sufficient evidence on its own.
  • What happens on failure: OMA checkpoints let you resume instead of rerunning; gate rollback behavior is unchanged — nothing auto-advances because a runtime reported success.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). CEO_REVIEW, scope changes, waivers, client acceptance and release stay human — OMA's onPlanPatch approval is an extra human checkpoint, not a substitute.
  • Smallest safe experiment: today's zero-key scaffold plus one gated two-agent run on a scratch folder; then decide whether the verified journal is worth exporting as gate evidence. Zero changes to Agency OS scripts.

Daily Learning: "fail closed" — the approval-gate failure mode of agent runtimes

  • Concept (simple English): when an approval system hits an unexpected state — missing record, stale hash, schema drift, tampering — it can either allow the action (fail open) or block it (fail closed). OMA's durable approval gates fail closed: anything suspicious about an approval blocks execution instead of proceeding.
  • How an AI agent might get it wrong: an agent "helpfully" proceeds when an approval record is unreadable, or a crashed gate callback defaults to allow, so unapproved consequential actions execute silently.
  • How you recognize the failure: runs that complete despite missing or malformed approval records; gate errors logged as warnings; approvals that survive refactors because nobody re-validates their schema.
  • What detects it: a rule that every gate decision must produce a persisted, content-bound record, and a verification step (like verifyRun()) that replays the journal and fails the run when evidence does not reproduce — exactly what gate_engine.py already demands before advancing.
