Start Here (plain English)

The problem: when a coding agent finishes "the work", the danger zone starts. Who reviews the change, who decides it can merge, and who pays for it? Most solo developers either review everything manually (you become the bottleneck) or let the agent self-approve its own pull requests (nobody is really reviewing). The hard half of a factory is not writing code, it is deciding what merges, and making that decision something an agent cannot make for itself.

The solution in today's radar: owainlewis/machinist, "a job runner for coding agents". One control plane holds every job; runners on your machines execute a preset pipeline (clone, implement, review by a second agent, fix, re-review, publish); and the merge itself is decided by code in the control plane once the repository's checks pass. The tool's own motto for it: "That rule is code, so no agent decides what merges." It also tracks money, with a Spending dashboard showing cost per merged pull request.

The Featured Factory: owainlewis/machinist — a job runner for coding agents TEST NOW

  • Link: github.com/owainlewis/machinist — a Go control plane plus small runner daemons that run predefined agent pipelines on machines you control (laptop, VM or Kubernetes), described as early-access, open-source software.
  • License (verified on GitHub, Nov 24, 2026): MIT (LICENSE file present, copyright Owain Lewis 2026).
  • Verified repo facts: 544 stars, Go, created Jul 16, 2026, last pushed today Nov 24, 2026. Latest commits: Nov 24 — README shows the job page and Spending dashboard (#700), failed steps keep their result.md as the failure report (ENG-131); Nov 23 — dashboard adds time to merge and human touches (ENG-177, PR #689), merges now happen from the control plane rather than a runner step (PR #687).
  • What it is (simple English): you assign work in one place (web app, a Linear issue, a schedule, or a curl call to the run API). A runner checks out the repository, an agent implements the change, a second agent reviews it, another step fixes what the review found, then it is reviewed again and Machinist opens one pull request. A control-plane step merges it once the repo's checks pass. Jobs run headless and "never stop to ask a question"; when the agent had to guess, it says so under Assumptions in the pull request.
  • Supported harnesses: Claude Code, Codex, Antigravity (Google) and Pi, each step with its own model and prompt. Shell commands are steps too. A test step is explicitly "a gate an agent cannot skip".
  • Classification: new public project from 2026 with steady, verifiable daily commits; an installer and stable releases with SHA-256 checksums plus nightly builds exist (so it is past "toy" stage, but self-described early-access).
  • Why it matters to a vibe coder: it separates three things most setups blur: who runs steps (runners), who decides merges (control-plane code plus your branch protection), and who pays (per-model, per-merged-PR spend tracking). That separation is exactly what a one-person agency needs before trusting an unattended build.
  • Costs (real): the software is MIT and runs locally for free, but the agent harnesses are not free: Claude Code/Codex/Antigravity run on their own subscriptions or API keys. GitHub usage is your own account/token. The dashboard tells you what that actually costs per merged pull request.
  • Windows compatibility: official installers are Linux and macOS (amd64/arm64) only. The control plane and runners are Go binaries, so Windows should work via WSL2, but that path is untested here; assume nothing for client machines. The production UI is committed, so no Node build is needed locally.

Honest Gaps

  • DISCOVERY and PROBLEM_DEFINITION: absent. The quality of the output is bounded by the prompt or spec you write. Agency OS's discovery and problem-definition gates stay external.
  • PROPOSAL and pricing: absent, by design. Keep commercial work in Agency OS.
  • RELEASE/deployment: absent. The pipeline ends at a merged (or open) pull request; staging and release are yours.
  • Product-level security scanning: SECURITY.md covers what a step may do and token scoping, but there is no SAST or dependency-scanning stage for the code it writes. Keep Agency OS's security stage and an external scanner.
  • Governance: there is no multistage gate engine or living project-state file like Agency OS's; enforcement lives in merge code, test-step gates and your branch protection. It complements gate_engine.py, it must never replace it.
  • Windows: no native Windows installer; WSL2 is the plausible path, untested here.
  • Maturity: self-described early-access; expect interface movement between releases.

Why It Fits Agency OS

  • Outside-the-agent enforcement: the merge decision is code in the control plane, and test steps are gates "an agent cannot skip" — the same constitutional pattern as gate_engine.py: rules the model cannot talk its way around.
  • Evidence and honesty over confidence: agents cannot stop to ask, so every guess must be declared in the pull request's Assumptions section, and failures keep their result.md. Silence about uncertainty is treated as a defect, matching Agency OS's "agents never invent facts or evidence".
  • Human approval is a flag, not a hope: github.auto_merge: false converts the whole factory from autonomous to human-approved without redesigning it; branch protection still has final say in both modes.
  • Provenance is measured: the dashboard records who reviewed, when a person stepped in, and time to merge; approvals are attributable, echoing Agency OS provenance discipline.
  • Specialized agents, orchestrated: per-step harness, model and prompt; implementer and reviewer are separate agents with separate instructions, avoiding the self-review failure mode.
  • Living, versioned factory state: presets, agents, prompts and scripts are commitable files; the production line evolves through ordinary Git review.
  • Compatibility status: plausible, untested. Nothing indicates machinist reads project-state.json or speaks Agency OS gates; its artifacts (PR, Assumptions, review records, step outputs) would enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • Auto-merge is the default: github.auto_merge is on by default, meaning merged PRs once checks pass. For any client repo, turn it off first. This is the single riskiest default for Agency OS governance.
  • Headless by design: jobs never pause to ask. The safety net is Assumptions plus test gates, not conversation. Only send work whose failure mode you can tolerate discovering later. Start with scratch repos, low blast-radius tasks and a Spending dashboard you check daily.
  • Model costs: Claude Code, Codex and Antigravity run on their own subscriptions or API keys; unattended pipelines can burn tokens on retry loops; mitigate it by starting with the local quick start and small prompts.
  • Windows: Linux/macOS installers only; WSL2 plausible but untested here. No verdict on Windows-native operation.
  • Early-access maturity: actively developed with near-daily commits, but self-described early-access; pin a stable release rather than living on nightly.
  • Human review points: job intake (the prompt), auto-merge setting, branch protection rules, and every merge on a client repository. Never delegate those.

Agency OS Integration Proposal: make machinist the DEVELOPMENT-to-CEO_REVIEW executor with the merge held for the gate engine

  • Problem solved: Agency OS lacks a hardened unattended executor: agents that implement, get reviewed by a second agent, record their assumptions and produce step-level evidence, without ever deciding a merge themselves.
  • Workflow improved: after the ARCHITECTURE gate exists, hand the SPECIFICATION artifact to machinist as the job prompt/spec; add one preset with a test step that runs an Agency OS gate-engine validation script; set github.auto_merge: false so every pull request lands in CEO_REVIEW with the gate approval as the human decision, then RELEASE proceeds as today.
  • Lifecycle point: DEVELOPMENT and QA executed by machinist; CEO_REVIEW stays human; LEAD, DISCOVERY, PROPOSAL and RELEASE untouched.
  • How results are validated: the preset's test step calls gate_engine.py on the produced artifacts, so an unvalidated advance fails in CI and the PR cannot enter merge. Machinist's own merge code and your branch protection remain the outside-the-agent enforcers; no governance, gate engine or project-state.json logic changes.
  • What happens on failure: check failures keep their result.md step output, visible in the job record, feeding the QA gate as evidence.
  • Smallest safe experiment: run one scratch-repo job with the default preset, auto_merge: false, and one extra test step that runs an existing Agency OS check on the diff. If the gate rejects a real change correctly and the Assumptions section honestly flags the agent's guesses, you have your evidence to widen the trial.

Daily Learning: "no agent decides what merges" — decision rights as code

  • Concept (simple English): machinist's core trick is not that agents are smarter; it is that the merge is a code path in the control plane, reachable only after checks pass, and the credential that merges lives with the control plane rather than with any runner or agent. In dark-factory terms, it removed the one lever that matters ("can this ship?") from the machines' hands while leaving them everything else.
  • How an AI agent might get it wrong: a review agent approves the work of its own model family, or the integrating agent "temporarily" relaxes a check, or a retry loop loosens a gate condition until something passes and merges.
  • How you recognize the failure: merges whose review and implementation share a model family; check runs that disappear before a merge; merged PRs with no recorded person or rule that permitted the merge; or dashboards where "human touches" trends to zero on risky repositories.
  • What detects it: keep merge credentials out of agents (control plane or GitHub App tokens only), record reviewer identity and time-to-merge for every merge, alert when a merge happens without a matching allowed rule, and let gate_engine.py refuse any release whose merge lacks an approvable provenance trail. The rule decides, the agent reports.
