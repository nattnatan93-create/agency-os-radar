Start Here (plain English)

The problem: AI coding agents say "Done — tests pass" about code they never tested, leak secrets into git history, and skip reviews when nobody checks. A rules file (Cursor Rules, AGENTS.md) only asks them to behave; they can ignore it. As a one-person agency, every fabricated "done" lands on your plate — or your client's production.

The solution in today's radar: KbWen/agentic-os adds the layer a rules file can't be: checks the agent doesn't control. A credential scan that fails the commit before a leaked key reaches git history, a validator that fails when a phase or its evidence is missing from the work trail, and a test-run recorder that stores the real exit code plus a fingerprint of the code — so "tests pass" is a machine receipt, not a claim.

Honest Gaps

  • LEAD and PROPOSAL stages — no client-facing, pricing, or proposal tooling. Agency OS keeps those.
  • Deployment / release automation — the ship gate ends at merge; no deploy, backup, or rollback stage.
  • Security beyond secrets — machine-enforced scanning covers credentials; broader SAST/dependency auditing is optional CI adoption, not a gate.
  • The fabrication blind spot (stated openly in the README): the validator checks the record the agent keeps — it catches a missing phase, not a faked record or a hand-typed "Test run: PASS" line. Only the secret scan and your real CI tests are checks the agent can't talk its way past. This mirrors Agency OS's REAL vs SIMULATED distinction — and it's why your gate_engine.py stays authoritative.

Why It Fits Agency OS

  • Evidence before advancing: every phase must leave a record with evidence; a missing one fails the validator — the same principle as Agency OS's validated-evidence rule.
  • Risk-scaled rigor: tiny-fix vs feature vs architecture-change paths — like Agency OS's QA scope (unit → UI-E2E) scaling to the change.
  • Single source of truth: a per-project state file carries decisions, evidence and gate receipts across sessions — philosophically the same job as project-state.json. It complements, never replaces it.
  • Human approval at the boundary: the ship gate stops the agent and hands the merge to you — matching Agency OS's human-approval rule for release.
  • Model-agnostic: the same Markdown governance works across Claude Code, Codex, Cursor, Copilot — matching a vibe coder's multi-IDE reality.
  • Agency OS compatibility: plausible — untested alongside your existing gate_engine.py/precommit_check.py stack until you run the experiment below.

Limitations, Risks & Human Review

  • Enforcement is opt-in: a fresh install runs nothing by itself — the git hook and CI job must be switched on (the installer prints both commands). Until then it's just a better rules file.
  • Local hook can be bypassed: --no-verify skips the pre-commit validator; work logs are gitignored, so CI cannot run phase checks — only the secret scan and your real test suite hold in CI.
  • Records vs reality: the validator catches gaps, not fabrications — keep human review on the artifacts, not just the trail.
  • Self-reported markers: the ⚡ ACX runtime marker only says the agent loaded the governance files; the persistent check is the validator warning.
  • Token cost: full-gauntlet features cost more model tokens; the project benchmarks this — read its model guide before wiring it into every client project.
  • Human review required: any adoption into a client project is a scope/commercial decision — your CEO_REVIEW approval, not the framework's.

Test Today: the credential-gate demo on Windows (~15 min)

  • Why this one: free (MIT), local, no subscription, no install — and it demonstrates the single most valuable behavior: a machine gate blocking a leaked secret with the value redacted.
  • Prerequisites: Windows with git, PowerShell 7 (pwsh), Python available on PATH (the scanner is a Python script; the repo docs also describe a no-Python mode for the full install).
  • Official steps: git clone https://github.com/KbWen/agentic-os.git, then from the repo root run pwsh demo/run.ps1 (bash equivalent: bash demo/run.sh).
  • Practical test: the demo has an "agent" write a config.env containing a fake aws_access_key_id and report "Done — config added", then runs the credential scan against it.
  • Expected results (per the README's documented demo): the scan prints CREDENTIAL PATTERN(S) DETECTED (values redacted) naming config.env:2: aws-access-key-id, and the commit is BLOCKED. The key is generated at runtime and redacted in output — the demo never stores a real secret.
  • Safety precautions: run only in a scratch clone; read demo/run.ps1 before executing it (never run untrusted code blindly); nothing installs, nothing hooks, nothing persists.

Agency OS Integration Proposal: machine receipts as gate evidence

  • Problem solved: your QA gate can accept an agent's claim that tests pass; and nothing today fails a commit that carries a leaked credential before it reaches history.
  • Workflow/agent improved: QA agent and security agent — adding a machine-checkable evidence format, feeding — never replacing — gate_engine.py and your existing precommit_check.py.
  • Lifecycle stages: QA and SECURITY.
  • Inputs: staged diff or changed files at commit time; the project's real test suite at QA time. Outputs: a credential-scan verdict with redacted findings, and a test-run receipt (exit code + code fingerprint) recorded as gate evidence in project-state.json.
  • How results are validated: the scan and the test run are executed by the machine, not reported by the agent; the QA gate advances only on a PASS receipt whose fingerprint matches the code being shipped.
  • What happens on failure: detected credential → commit blocked, secret rotated, change removed, retry; failed or stale test run → gate stays BLOCKED until a fresh PASS receipt exists.
  • Gate or human approval? No governance change: the gate engine keeps its current transitions; waivers and scope changes still need your human approval. This only tightens the evidence the existing gates consume.
  • Smallest safe experiment: run the demo above in a scratch clone; separately run scan_credentials.py --staged on a staged throwaway file containing a fake key in a scratch repo, and wire the result into precommit_check.py as one extra check. One commit, one blocked secret, one receipt — then decide.

Daily Learning: a validator checks the record, not reality

  • Concept (simple English): a gate can verify two different things — that a record exists (phase done, test logged) or that the thing the record describes actually happened. Most agent-workflow validators do the first; only checks that re-execute the work (a scanner, a real test run) do the second.
  • How an AI agent might get it wrong: it writes a plausible "Test run: PASS" line into the work trail by hand, or copies last week's receipt for today's changed code.
  • How you recognize the failure: the record is present and formatted perfectly, but there's no machine receipt — no exit code, no code fingerprint, no timestamp tying the run to the current code.
  • What detects it: agentic-os's record_test_run.py (stores exit code + code fingerprint; the ship gate fails if the code changed after the PASS receipt) and its credential scan; in Agency OS, the same failure class is caught by prepush_release_check.ps1 re-running the suite rather than trusting the log.
