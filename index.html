Start Here (plain English)

The problem: a vibe coder's biggest silent risk is an AI agent grading its own work. The same agent writes the code, writes the tests, and "reviews" the result — then reports success. The client finds out later, in production. Babysitting every step kills your throughput; walking away kills your credibility.

The solution in today's radar: zeroshot, an MIT-licensed workflow engine for coding agents. You write your development and QA process as a graph of implementation, independent review, testing, repair and delivery. Agents do the work; the graph decides what happens next, and the engine enforces its transitions and retry limits. A different agent reviews every change, and no change merges until tests and both reviews pass.

The Featured Factory: Zeroshot TEST NOW

  • Link: github.com/the-open-engine/zeroshot · docs: zeroshot.sh/docs
  • License (verified from the LICENSE file): MIT.
  • Verified repo facts (GitHub, Nov 10, 2026): ~2,100 stars; release v13.1.0 published today (Nov 10, 04:51 UTC) and commits today, including a fix that removes secret-bearing temporary store files left behind by interrupted saves. This is an update to an established, fast-moving project, not a new project.
  • What it does (simple English): an open-source workflow engine for coding agents. You define your process as a graph (implementation → independent review → adversarial test → PR → CI → merge, with repair loops on every rejection); the engine runs it with your agents, records every step's result in a run ledger, and cannot be talked out of the graph by the model — "model output cannot add an edge or raise a bound." Built-in graphs include software-change (implement + acceptance review + code review + repair + deliver), single-worker, pr-review, code-review and auto-research. Runs locally in any folder or on self-hosted targets.
  • Why it matters to a vibe coder: it mechanizes exactly the discipline a one-person agency needs — no self-review, independent rejection paths, evidence (the run ledger) before anything merges — without renting a platform.
  • Costs (verified status): the software is free (MIT). Real costs are your model provider APIs (Claude Code / Codex subscriptions or tokens). No external cloud service is required for local runs. Open source ≠ free model access.
  • Windows compatibility: installs via npm (npm install -g @the-open-engine-company/zeroshot); the repo's CI includes a native Windows test lane (verified from a commit message). Windows status: plausible, UNTESTED on this PC.

Why It Fits Agency OS

  • Process as code: the graph, not the agent, owns control flow — the same philosophy as gate_engine.py, and the engine enforces transitions and retry limits the way your gate engine enforces lifecycle transitions.
  • No invented authority: model output cannot add edges or raise bounds — an agent cannot talk its way past the process, matching your "agents must never invent facts/approvals/evidence" rule.
  • Evidence before advancing: every step's result is recorded in the run ledger, giving the trail your "evidence must be validated before advancing" rule needs.
  • Author/reviewer separation: a different agent reviews every change, attacking the self-grading failure mode directly.
  • Compatibility status: plausible, untested. It complements the gate engine and never replaces it; no evidence yet that it reads project-state.json.

Limitations, Risks & Human Review

  • No human approval gate in the built-in graphs: agent reviews replace you reading the diff. Under Agency OS rules, CEO_REVIEW, scope changes, waivers, client acceptance and release still require a human — keep those in the gate engine.
  • A reviewer agent can still be wrong or rubber-stamp; the run ledger makes that visible, but a human still reviews verdicts at gates.
  • Fast release cadence (v13.0.0 and v13.1.0 one day apart): pin the version you install.
  • Runs continue after the terminal closes and consume model tokens; keep first runs on a scratch repo with scoped permissions, never unrestricted computer access.
  • Windows is plausible (npm + CI lane) but untested on this PC.

Agency OS Integration Proposal: Zeroshot as the QA-stage author/reviewer separation

  • Problem solved: today the dev agent's QA evidence rests on prompts; nothing mechanistically prevents an agent from grading its own work.
  • Workflow improved: the orchestrator's DEVELOPMENT → QA loop — dev agent implements, a second agent reviews, tests gate both, repair loops on rejection.

Daily Learning: the self-grading problem (author/reviewer separation)

  • Concept (simple English): an AI agent that wrote code tends to approve it. The control is structural: a different agent reviews, and tests written from the spec (not from the code) must pass before anything advances.
  • How an AI agent might get it wrong: it writes tests after the code that merely mirror the implementation, or produces a "review" that restates the diff without criticizing anything, then declares the work done.
  • How you recognize the failure: tests that never failed once; review notes that only summarize; zero rejected drafts in the run history.
  • What detects it: zeroshot's author/reviewer separation plus your precommit_check.py; under Agency OS rules the gate engine rejects a QA transition whose evidence is UNVERIFIED.
