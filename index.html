The Featured Factory: Paperclip — the company layer for your AI agent workforce TEST NOW

  • Link: github.com/paperclipai/paperclip · npm: paperclipai · docs: docs.paperclip.ing · maintained by Paperclip Labs, Inc.
  • License (verified from the LICENSE file): MIT.
  • Verified repo facts (GitHub, Nov 15, 2026): a commit merged today, Nov 15, 2026 at 14:09 UTC (perf fix #21758 on the remote-run sandbox path); the maintainers state over 2,700 merged pull requests; the v2026.1106.0 release page reports 2,566 commits to master since that release, confirming very high daily activity. Star count was not independently verified in this check, so none is quoted.
  • What it does (simple English): a Node.js server plus React dashboard you self-host (embedded PostgreSQL included, no setup). You define a goal, hire agents into an org chart (CEO, CTO, engineers, any harness that can receive a heartbeat), and agents wake for assigned work, follow-ups, schedules or routines. Around that sit the governance features: ticket tasks with atomic checkout and execution locks, review and approval stages, budget tracking with warning thresholds and hard stops that pause work, scoped secrets, connection permissions (Allowed / Ask first / Off), revisioned configuration with safe rollback, and a durable activity log for auditing who did what and why.
  • Recent verified changes: latest release v2026.1106.0 (Nov 6, 2026): the native Paperclip Runner is now the default for new Claude, Codex, OpenCode and Pi agents (qualified macOS and Linux hosts; Linux needs GNU libc 2.39+), GitHub Copilot joins as a native harness, project repositories auto-import as skill sources, model-backed prompt-injection prevention, agent observability to Braintrust or any OTLP endpoint, and workspaces that compact and expire themselves with encrypted restore points. Breaking changes in that release: the Pipelines experiment was removed, run failures no longer reach Sentry by default, and the run-history API is bounded to 200 rows by default (max 1,000). This is a new release of an established project, not a new project.
  • Why it matters to a vibe coder: it does not replace your AI IDE; it replaces the missing management layer. Sessions persist across reboots, one agent owns one task at a time, spend is capped, approvals are enforced, and every run leaves a record you can show a client.
  • Costs (verified status): the software is free (MIT) and self-hosted with no account required; a hosted Paperclip Cloud exists as a waitlist product. Real costs: your agents' own subscriptions or API keys (Claude, Codex, OpenRouter, etc.), and an optional Postgres for production. Open source ≠ free model access.
  • Windows compatibility: requires Node.js 24.11+; the native Runner defaults only on macOS and qualified Linux hosts, and Windows is not listed among them, so on Windows you would run the legacy adapter path or Docker. Status: plausible but UNTESTED on this PC, and the newest Runner path is not a Windows default.

Honest Gaps

  • RELEASE/deployment: nothing builds, versions or deploys. Uncovered.
  • PROPOSAL / client artifacts: no quotes, proposals or client-facing documents; artifacts are internal tasks, plans and documents.
  • ARCHITECTURE documents: workspaces and worktrees are structure, not a reviewable architecture artifact.
  • SECURITY (code-level): Paperclip governs who may act and what tools may do, but does not scan generated code for vulnerabilities. A dedicated scanner such as Semgrep is the classic gap-filler; treat as a candidate to verify separately, not as verified advice.
  • Gate engine: no project-state file, no lifecycle transition enforcement, no gate rollback engine. Its approvals and activity log are the raw material for gate evidence, not the gates themselves.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: an org chart of role-typed agents (CEO, CTO, engineers) with delegation up and down reporting lines, woken by a server-side heartbeat queue — the orchestrator-plus-specialists shape, with the human as the board above it.
  • Agents must never invent facts or approvals: approvals are a server-enforced stage, not an agent promise; connection actions default to Ask first; and the release notes added model-backed prompt-injection prevention, defending the very channel (agent instructions) an attacker would poison.
  • Evidence validated before advancing: configured task reviews govern completion, watchdogs enforce outcomes, and every run produces logs, usage records and artifacts — completion claims are checked against recorded evidence, not accepted from the agent.
  • Human approval points: plan approvals, board approval workflows, one-time or rule-based connection approvals — scope changes and consequential actions stay human, matching Agency OS's rule for commercial decisions.
  • Living state: durable activity log, revisioned configuration with safe rollback, and persistent task context across reboots — the control-plane equivalent of an authoritative state file.
  • Compatibility status: plausible, untested. Nothing in the docs shows Paperclip reads project-state.json or enforces Agency OS lifecycle transitions, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • Windows is not a first-class Runner target: the new native Runner defaults on macOS and Linux (glibc 2.39+); on Windows expect the legacy adapter path or Docker. Untested on this PC.
  • Fast-moving, big-bang releases: v2026.1106.0 shipped 515 commits with four breaking changes (Pipelines removed, Sentry defaults changed, bounded run-history API, a CLI flag now required). Pin a version and read the Breaking Changes section before upgrading.
  • Telemetry is on by default: anonymous usage telemetry ships enabled; disable it with PAPERCLIP_TELEMETRY_DISABLED=1, DO_NOT_TRACK=1, or config if that matters for client work.
  • Autonomy costs money: agents running 24/7 with heartbeats and routines consume real tokens; use company, agent and project budgets with hard stops on anything unattended.
  • Company-package sharing leaks context: export packages omit referenced secret values, but the docs warn plain environment values and local paths can remain; review packages before sharing.
  • Budget stops are not instant: enforcement uses recorded spend, so in-flight work can delay a hard stop — keep human review for anything with external side effects.

Agency OS Integration Proposal: Paperclip as the governed work queue and audit trail in front of Agency OS agents

  • Problem solved: Agency OS currently tracks state in project-state.json and gate decisions, but the day-to-day agent work (who owns which task, what a run cost, who approved what) lives in scattered terminal sessions; Paperclip supplies ticketed, locked, budgeted, audited work management.
  • Workflow improved: DEVELOPMENT execution — each Agency OS task becomes a Paperclip ticket assigned to one coding agent, with review stages and budget hard stops around it.
  • Lifecycle point: DEVELOPMENT (atomic checkout, runs) plus CEO_REVIEW (approval stages) and MAINTENANCE (activity log, run history, rollback of config changes).
  • Inputs and outputs: an approved Agency OS task description in; run logs, usage records, artifacts and approval records out.
  • How results are validated: gate_engine.py treats Paperclip run records and approvals as candidate evidence only; QA evidence still comes from your own test runs, and a human confirms before any gate advances. A Paperclip "completed" task is never sufficient evidence on its own.
  • What happens on failure: Paperclip's bounded recovery and watchdogs handle or surface failed runs; gate rollback behavior is unchanged — nothing auto-advances because a ticket closed.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). CEO_REVIEW, scope changes, waivers, client acceptance and release stay human.
  • Smallest safe experiment: today's test-drive run with one agent and a $1 budget; if the audit trail is useful, pilot one real project's DEVELOPMENT tickets through a local Paperclip instance. Zero changes to Agency OS scripts.

Daily Learning: "atomic task checkout" — the double-claim failure mode of agent teams

  • Concept (simple English): when several agents can pick up work, two of them can start the same task at once, overwrite each other's files, and both report success. Atomic task checkout means a task has exactly one assignee and an execution lock: the second agent's claim is refused, not queued into a conflict.
  • How an AI agent might get it wrong: an orchestrator assigns work by prompt only ("someone fix the login bug"), two eager agents both start, git history tangles, and each agent's completion report looks valid because neither saw the other.
  • How you recognize the failure: two branches touching the same files for the same issue; duplicated work products; merge conflicts that "nobody" created; token spend roughly double for one task.
  • What detects it: a rule that every work item must be claimed through a system that records assignee and lock state durably (a ticket system or project-state.json with a lock field), and a gate check that refuses to advance any task with more than one live claim — the same single-writer discipline gate_engine.py applies to lifecycle transitions.
