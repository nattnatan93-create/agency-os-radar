Test Today: NVIDIA SkillSpector

  • Why this one: fully local, free, no API keys, no subscription, Python-based — realistic on a Windows PC with an AI IDE in under an hour. It also addresses the riskiest habit a vibe coder has: installing third-party skills.
  • Prerequisites: Python 3.10+ and pip (or uv) on Windows; git.
  • Official install steps (from the repo): create and activate a virtualenv first (the Makefile assumes it); install with uv or pip; then run skillspector scan against a skill directory. Follow the repo README exactly — it is the authoritative source; if a Makefile step fails on Windows, run the underlying commands manually rather than improvising.
  • Practical test: pick one skill you already use or are considering installing; run the scanner on its folder; read the report.
  • Expected results: a risk report with a 0–100 score, severity rating, per-file findings (e.g., env-variable harvesting), and a recommendation such as DO NOT INSTALL for dangerous patterns.
  • Safety precautions: run inside a virtualenv; never pipe install scripts straight into a shell without reading them; scan copies, not live installs; a HIGH score means stop — do not install to review it. Never give any scanner unrestricted computer access.

Agency OS Integration Proposal: SkillSpector as SECURITY-stage evidence

  • Problem solved: REUSABLE_COMPONENT onboarding and skill adoption currently have no automated security evidence — the security agent would have to rely on claims (SIMULATED/ASSUMPTION) instead of artifacts.
  • Workflow improved: security agent's component/skill intake check.
  • Lifecycle location: SECURITY stage, plus the REUSABLE_COMPONENT stage when a skill is promoted for reuse.
  • Inputs: a skill/MCP package directory (local copy).
  • Outputs: a SkillSpector risk report stored as project evidence with REAL classification and the scan date/version.
  • Validation: evidence must be validated before advancing: report exists, scanner version recorded, findings triaged by the security agent; findings marked VERIFIED only after a human reads the flagged lines.
  • On failure: any HIGH finding marks the component BLOCKED; the security agent records BLOCKED in project-state.json with the report as evidence. BLOCKED components cannot advance without an explicit human waiver.
  • Gate blocking / approval: it feeds the existing SECURITY gate as evidence — it does not replace the gate engine. A waiver (accepting a flagged component) is a scope/safety decision → human approval required, per governance rules.
  • Smallest safe experiment: in a virtualenv, scan one existing skill you already use; save the report; have the security agent classify findings REAL/SIMULATED/UNVERIFIED. No production change, no gate modification. Cost: ~30 minutes.

Daily Learning: Skill supply-chain risk (prompt injection & exfiltration)

  • Concept: an AI "skill" or plugin is code plus instructions that your agent will follow. A malicious one can embed instructions that redirect the agent ("send this .env file to help debug") — the agent follows them because instructions look authoritative. That's prompt injection; shipping the data out is exfiltration.
  • How an AI agent gets it wrong: it treats a skill's README as trusted documentation and recommends installing it based on its own description — reasoning from the attacker's own words.
  • How you recognize the failure: an adoption recommendation with no scan artifact behind it; evidence classed as VERIFIED when it's actually UNVERIFIED.
  • Which tool/test detects it: SkillSpector scan before install, plus your own rule: no skill enters an Agency OS environment without a stored scan report.
