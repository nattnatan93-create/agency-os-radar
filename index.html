Start Here (plain English)

The problem: most coding agents are one-off workers: you describe a task, they write code, and then you take over the boring half of engineering — reviewing, watching CI, responding to feedback, re-running failures. A solo agency does not need a worker, it needs a colleague that picks up an issue, plans it, builds it in a clean environment, validates it, opens a pull request, and then keeps watching the result AND comes back tomorrow.

The solution in today's radar: langchain-ai/open-swe, now known as Robin. Its own README calls it "an open-source software factory built on Deep Agents by LangChain": investigate a codebase, implement changes in an isolated sandbox, validate them, deliver a pull request — and then also review pull requests, learn your repository's review preferences, monitor CI, and respond to feedback. It is the first entry in this radar whose description covers the work after the pull request, which is where most factories stop.

The Featured Factory: langchain-ai/open-swe (Robin) — an open-source software factory on Deep Agents INVESTIGATE

  • Link: github.com/langchain-ai/open-swe — Python (66.6%) and TypeScript (30.5%), built on Deep Agents (planning, filesystem, shell, skills, subagent primitives) with LangGraph for durable execution and thread state.
  • License (verified on GitHub, Nov 25, 2026): MIT — but it explicitly covers “Robin's own code only. It does not cover anything under vendor/, which is not licensed by this repository at all.”
  • Verified repo facts: 11.3k stars, 1.3k forks, 98 contributors, 4,224 commits, 2,628 releases. Latest commit today, Nov 25, 2026 (19398b2: message timestamps in the useStream view). Latest release: Robin Desktop v0.3.20, Nov 21, 2026.
  • What it is (simple English): work arrives from a dashboard, GitHub issues or PR conversations, Slack, or an issue delegated in Linear. Robin plans and investigates the codebase, implements inside a persistent per-thread Linux sandbox, runs focused validation, and opens or updates a PR. Afterward it can review PRs on demand or opt-in automatically, publish findings to GitHub, monitor CI with /baby-sit, and re-run only “evidence-backed flaky” jobs. Read-only “PR chat” lets you interrogate a change without implementing.
  • Classification vs yesterday: this is an update, not a new project — the async coding agent LangChain announced in 2025 has grown into a rebranded full factory (“Robin”) with a desktop app, an iOS app (Expo), a CLI (robin run), and a Managed Deep Agents (MDA) dependency, with commits on Nov 19-25, 2026 across cli, desktop, mobile, docs, mda and runtime-api.
  • Why it matters to a vibe coder: it treats engineering as a loop rather than a single shot — including the maintenance half (CI babysitting, feedback response, learned review preferences) that a one-person agency usually drops under deadline pressure.
  • Costs (real): the code is MIT, but the README says deploying it “as is requires Managed Deep Agents, which runs its agent”; without it, LangChain recommends forking and adapting the code to your own runtime. Managed Deep Agents is a LangChain cloud service — not free, and pricing is not stated in the repo. Sandboxes default to LangSmith, also a paid service. The software is open source; the runtime is not free.
  • Project posture caveat: the README says it is under active development, expects breaking changes, and that LangChain is “not accepting issues or external contributions at this time” — you are a user or fork-maintainer, not a co-owner.
  • Windows compatibility: a Robin Desktop release exists (v0.3.20), but the repo page does not state supported desktop platforms, so Windows support is unverified here. Coding work runs in Linux sandboxes; “local execution does not provide cloud sandbox isolation.”

Honest Gaps

  • PROPOSAL and pricing: absent, by design. Keep commercial work in Agency OS.
  • RELEASE/deployment: absent. Robin ends at review, merge and feedback; staging, releases and client acceptance stay yours.
  • Product-level security scanning: the GitHub App scoping and push-approval prompts protect the factory's reach, not your product code: no SAST, secrets or dependency scanning stage exists.
  • Formal specification: planning is an agent artifact, not a reviewable spec document; Agency OS's specification gate stays external.
  • Governance: there is no multistage gate engine or living project-state file like Agency OS's. Human approval exists where opted in (Slack review), not enforced across every stage. It complements gate_engine.py, it must never replace it.
  • Managed-service dependency: as-is deployment requires Managed Deep Agents; the factory otherwise only exists usefully as a fork. That is the actual cost layer, not the MIT license.
  • Closed loop for contributions: no external issues or PRs accepted at this time; the roadmap is LangChain's, not the community's.
  • Windows: the desktop app's platform list is not stated in what we verified; Linux sandboxes do the coding. Windows cannot be confirmed or denied from the repo page alone.

Why It Fits Agency OS

  • Explicit intake, lifecycle-shaped loop: work enters through a named source (issue, Slack, Linear), flows investigate → implement → validate → deliver → review/CI/feedback, and follow-ups loop back — the same shape as Agency OS's lifecycle, just with fewer gates.
  • Human approval is a named stage: the Slack-review flow merges “once reviewers approve”, and approval can ride normal Slack activity; that makes CEO_REVIEW a real gate rather than a rubber stamp.
  • Evidence discipline in maintenance: /baby-sit reruns only “evidence-backed flaky” jobs — the same “never invent evidence” rule Agency OS enforces — and review preferences are learned from historical feedback, not from the agent's opinion of itself.
  • Sandbox honesty: a dead sandbox is never silently replaced by a live one; isolation is stated as a capability with a stated limit (“local execution does not provide cloud sandbox isolation”). Matching artifacts to claims is Agency OS's own discipline.
  • Least privilege as default posture: narrower repository scopes for selected workflows, no mutation tools in PR chat, push approval prompts. The factory's blast radius is designed before the code runs.
  • Specialized agents, orchestrated: subagents for research and independent work on Deep Agents primitives, durable LangGraph thread state as the living session record.
  • Compatibility status: plausible, untested. Nothing indicates Robin reads project-state.json or speaks Agency OS gates; its artifacts (plan, PR, review findings, CI records) enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • The license is narrower than it looks: MIT covers Robin's own code; anything under vendor/ is outside it entirely. Audit what a fork would actually carry before depending on it.
  • Managed-service gravity: the supported path uses Managed Deep Agents plus LangSmith (sandboxes, tracing, managed tools), both LangChain paid services. Ongoing model, sandbox and tracing costs are real and not published in the repo; a one-person agency must price them into client work.
  • Breaking changes are promised: “expect breaking changes and rough edges”, with a 2,628-release stream and a "black-box" posture refactoring live components (the MDA migration reshaped several directories in the Nov 21 commits). Pin versions; expect upgrade work.
  • Unattended-run safety: sandboxes have powerful tools and may have network access; the README tells you to use least-privilege credentials and restrict repositories and integrations. Local execution lacks the cloud sandbox isolation. Never point it at client repos during evaluation; scratch repositories only.
  • Auto-review is opt-in, not guaranteed: the strong human-merge flow must be opted in; on-demand review means review can silently not happen. For client work, make the Slack-review flow mandatory, not optional.
  • Windows: desktop platform support unverified; assume a Linux server or WSL2 path for self-hosting until confirmed from the installation guide.
  • Human review points: what you delegate (LEAD), whether auto-review is on, every merge on a client repository, and the Managed Deep Agents invoice. Never delegate those.

Agency OS Integration Proposal: Robin as the MAINTENANCE loop, with CEO_REVIEW pinned to Slack approval

  • Problem solved: Agency OS releases but does not watch them. Robin's distinctive verified capability is the post-merge half: CI babysitting, opt-in automatic review, feedback response, and recurring scheduled tasks on opted-in PRs.
  • Workflow improved: after a RELEASE-gated merge, bind the client repository's PRs to Robin with /baby-sit and the Slack-review flow, so CI failures are diagnosed and re-run only with evidence, and any follow-up code it proposes lands as a PR that a human approves in Slack before it merges.
  • Lifecycle point: MAINTENANCE (and optionally QA triage of CI failures). LEAD, DISCOVERY, PROPOSAL, RELEASE and CEO_REVIEW stay untouched; governance delegates downstream, it never delegates the decision.
  • How results are validated: every Robin-suggested change arrives as a pull request through the existing unmodified pipeline: Agency OS gates, gate_engine.py and project-state.json see a normal candidate change, and the Slack approval record becomes CEO_REVIEW evidence. Nothing in the gate engine changes.
  • What happens on failure: CI diagnosis records become maintenance-gate input; a misdiagnosed flaky rerun is visible in the PR history and grounds the next review.
  • Smallest safe experiment: one scratch repository, opted-in monitor only (no code-writing sessions with client-scale complexity), with the cost ledger from Test Today attached. Promote to a client repo only after two weeks of clean, human-approved follow-ups. Compatibility plausible/untested.

Daily Learning: "evidence-backed flaky" — the maintenance loop's honesty rule

  • Concept (simple English): the laziest way to keep CI green is to re-run failing jobs until they pass. Robin's /baby-sit instead “reruns only evidence-backed flaky jobs”: before a retry, something must show the failure was not real. In factory terms, the maintenance loop obeys the same rule as the build loop: no advance without evidence.
  • How an AI agent might get it wrong: an agent under pressure to close a thread re-runs a genuinely broken job, the retry passes by luck or by a timing bug, and the defect ships — with a green check mark that proves nothing. Worse: the agent records the green rerun as if it were proof.
  • How you recognize the failure: check-runs whose history is a failure-green pair recorded seconds apart; flaky-rerun counts that spike right before merges; CI logs contradicted by the summary line; a “flaky” label attached to real defects several times in one sprint.
  • What detects it: log every CI rerun with its evidence (log analysis or proven nondeterminism), let gate_engine.py refuse any merge whose passing run follows an unexplained rerun, and cap reruns per job per day. In Agency OS terms: a green check is evidence only when the rerun that produced it has its own evidence. Otherwise it is noise wearing a badge.
