Start Here (plain English)

The problem: most "AI factory" tools are platforms you must host, or bundles of prompts whose influence lives in your head. For a one-person agency, the real leap is a factory whose whole setup is a readable folder checked into the repository itself: who works, when they start, and exactly what they are allowed to do — versioned, reviewable, and diffable like any other code.

The solution in today's radar: openfabriq/openfabriq, "your AI software factory, as code." You describe your team of Claude agents in an openfabriq/ folder (a factory.yaml, one small job description per agent, one automation per trigger). A local engine watches your repository, runs the right agent in a sandboxed checkout, runs your checks, then pushes only the GitHub actions the automation's can list allows — and a person always merges.

The Featured Factory: openfabriq/openfabriq — your AI software factory, as code TEST NOW (scratch repo only)

  • Link: github.com/openfabriq/openfabriq — a TypeScript engine that runs a team of Claude Code agents on your GitHub repository, described in readable files in an openfabriq/ folder, running on your machine or your team's server.
  • License (verified on GitHub, Nov 22, 2026): Apache License 2.0 (LICENSE file present, added with the first public release; the org page badge and documentation both confirm Apache-2.0).
  • Verified repo facts: 30 stars, 5 forks, 49 commits, 10 open issues, TypeScript, updated Nov 19, 2026. Created and maintained by Matthieu Guirlinger. Small and new — treat everything accordingly.
  • What it is (simple English): the factory is a folder. factory.yaml names the repository, the maintainers whose actions may start runs, the model tier, the test/lint commands, the checks the engine runs before code leaves the machine, and hard limits (for example usd_per_run: 5, usd_per_day: 30). One markdown file per agent is its job description; one markdown file per automation says when it starts (an issue label, a review, a cron, a Slack/Linear/Sentry/webhook event), which agent runs, and what the engine may write to GitHub on its behalf.
  • Classification: new project. Version 0.1.0, its first public release, landed Nov 16, 2026; installation is via Homebrew or npm (Node.js 24+).
  • Verified recent change (last 4 days): Nov 19 commits "fix(factory): build before the typecheck check" (#70) and a cron-interval fix (#59); Nov 18: AGENTS.md docs and CI-tooling fixes; CHANGELOG synced Nov 19. The repository famously runs its own factory: its issues are triaged by it and some of its merged pull requests were opened by it.
  • Why it matters to a vibe coder: it turns factory construction itself into code you can openfabriq plan and review, with security-relevant changes (a command the machine will run, a new maintainer, a new agent tool or automation right) listed first. That is a governance workflow, not just automation.
  • Costs (real): the engine is open source, but agents run on your Claude Code subscription (single-person use) or an Anthropic API key on a server; the optional Slack/Linear/Sentry/webhook relay needs either a free Cloudflare account (a small server you deploy once) or your own machine with Docker. Hosting the engine is free only because your machine pays for it.
  • Windows compatibility: not supported directly. The README requires macOS or Linux; on Windows the realistic path is WSL2. There is a openfabriq doctor command that lists missing sandbox packages on Linux. Untested on Windows here — assume nothing for client machines.

Honest Gaps

  • PROPOSAL and pricing: absent. Commercial work stays in Agency OS, as it should.
  • RELEASE/deployment: the factory's output is a merged pull request. Staging and deployment are outside the tool.
  • Code-level security scanning: the security model protects the machine (sandbox, credentials, network, prompt-injection containment), not your product. There is no SAST or dependency-scanning stage; keep Agency OS's security stage and an external scanner.
  • Single-vendor agents: agents are Claude Code sessions (the pinned foundation of the whole engine). No Codex/OpenCode/Gemini support is described.
  • Scale and maturity: version 0.1.0, 49 commits, one dominant maintainer. Expect rough edges and breaking changes; do not build a client deliverable on it yet.
  • Governance: there is no project-state.json, no gate engine and no rollback machinery in the Agency OS sense. Its permission model complements gate_engine.py; it never replaces it.

Why It Fits Agency OS

  • Agents never invent authority: agents hold no GitHub token, no gh login, no git credentials; they propose outputs and the engine applies only what the automation's can list allows. The approval always remains a person's merge — the same human-approval discipline Agency OS enforces at CEO_REVIEW and RELEASE.
  • Evidence before advancing: the engine itself runs the configured checks before code leaves the machine, and an agent's "done" is only validated output (check-passing PR with evidence in the description), not a claim.
  • Content is data: issue text, comments, Slack threads and webhook bodies reach agents marked as data, never as instructions — a direct mitigation of the "agent invents facts from untrusted input" failure mode.
  • Living, reviewable state: the factory's configuration is a folder in the repo, and openfabriq plan shows every change with security-relevant ones first, before apply. A pull request cannot change the rules that judge it, because the engine reads the applied copy, not your branch.
  • Specialized agents, orchestrated: narrow job-description agents (implementer, reviewer, docs keeper) coordinated by automations — the same orchestrator-plus-specialists pattern Agency OS assumes.
  • Compatibility status: plausible, untested. Nothing shows openfabriq reading project-state.json or enforcing Agency OS transitions; its artifacts would enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • Version 0.1.0 caution: first public release Nov 16, 2026; a single dominant maintainer; 30 stars. Feature behavior may change without notice; pin versions and expect migration friction.
  • Windows: macOS or Linux required; use WSL2 on Windows. Untested here — verify before promising anything to a client.
  • Model costs: agents are Claude Code sessions. A subscription is scoped for one person's own use; a team/server setup needs an Anthropic API key. Spending limits (usd_per_run, usd_per_day) exist precisely because unattended runs can burn tokens — set them on day one, low.
  • Unattended-run safety: any automation that opens PRs can produce plausible-but-wrong work. Keep your first automations to docs fixes and tiny bugs on a scratch repository, and rely on the engine's needs-human label for loops that hit review_rounds limits.
  • Known-security limits, honestly noted: the README itself flags remote MCP servers as outside the network allowlist — the project points at its own limits instead of hiding them, but read the security model before connecting any.
  • Human review points: merge is human-only; factory configuration changes go through plan (security changes listed first) and apply confirmation. Do not delegate those, ever.

Agency OS Integration Proposal: factory-as-code + plan/apply as a REUSABLE_COMPONENT gate artifact (not a new engine)

  • Problem solved: Agency OS's factory knowledge lives partly in prompts and partly in project-state.json, so reuse across projects means copy-paste from memory. openfabriq demonstrates declaring an agent factory as versioned files with an explicit permission surface.
  • Workflow improved: the REUSABLE_COMPONENT stage: when Agency OS generalizes a workflow, express the agent part as an openfabriq/-style folder (agent job descriptions + automations + an explicit can list), and require the openfabriq plan security-first diff as the artifact a human reviews before anything changes.

  • Lifecycle point: REUSABLE_COMPONENT gate and the ARCHITECTURE review of agent permissions. Authority boundaries (can lists, maintainer-only starts, spending limits) are documented as artifacts, exactly like any other spec.
  • How results are validated: gate_engine.py still validates artifacts and enforces transitions; the folder and its plan diff are candidate evidence like any other. No governance, gate engine or project-state.json logic changes.
  • What happens on failure: if the folder or its plan diff is missing or inconsistent, the gate blocks exactly as it does today.
  • Smallest safe experiment: rewrite one existing reusable Agency OS agent prompt as an agent.md + automation.md pair with an explicit can list, and check whether writing the permissions down surfaces any action the agent currently assumes it can take. If yes, keep the format; if not, discard — nothing in Agency OS changed.

Daily Learning: least privilege for agents — propose, never push

  • Concept (simple English): openfabriq's agents have zero write access: no token, no gh login, no git credentials. Everything an agent "does" to GitHub is a proposed output, applied by the engine only if the automation's can list allows it. Capability is declared in data, understood by an engine, and reviewed in a plan/apply diff — not implied by a long prompt.
  • How an AI agent might get it wrong: a capable agent is also an encouraged one: handed credentials "just for convenience," it will happily close issues, edit labels, push to main or rewrite CI to make failing checks pass — not from malice, but because nothing bounded it.
  • How you recognize the failure: your diff, labels or CI configuration contain changes nobody approved; the agent's transcript says "I pushed the fix" instead of "I propose the following change for your review."
  • What detects it: keep credentials out of agent environments entirely, declare allowed actions explicitly and enforce them outside the agent, and treat any write outside the declared list as a failed gate. In Agency OS, gate_engine.py is exactly that outside-the-agent enforcer — the same pattern at project scale.
