Agency OS Radar

Daily open-source discoveries for a one-person AI software agency
Report date: Thursday, November 12, 2026 · Agency OS Edition · Addis Ababa (EAT)

Start Here (plain English)

The problem: when you hand a whole feature to one coding agent, it plans, codes, "tests" and declares victory in a single context. Nobody checks the plan, nobody reviews the code, and when it fails it just retries the same way. A one-person agency needs the opposite: a team where planning, building, reviewing and verifying are separate jobs that check each other's work.

The solution in today's radar: SWE-AF, an Apache-2.0 "autonomous engineering team runtime": one API call spins up a coordinated fleet of specialist agents — product manager, architect, tech lead, sprint planner, coders, QA, code reviewer, merger, integration tester, verifier — that decomposes a goal into a dependency-sorted issue DAG, builds each issue in an isolated git worktree, reviews and tests every issue, merges, integration-tests, verifies acceptance criteria against the PRD, and opens a pull request with a post-PR CI gate.

One featured factory per day, per the format confirmed Nov 5, 2026 (re-confirmed Nov 10, 2026). Repo facts, license and commit activity verified directly from GitHub on Nov 12, 2026. Prior reports featured Orkas, dsh-superagent, Betterleaks, Spec Kit, CodeAF, Fabro, zeroshot, dzhng/skills and OpenHands, so today's factory is not a repeat. Disclosure: SWE-AF comes from the same organization (AgentField) as the previously featured CodeAF, but it is a different project — CodeAF is a single coding harness; SWE-AF is the multi-agent factory built on the AgentField control plane. Agency OS compatibility is marked plausible/untested, never assumed.

The Featured Factory: SWE-AF (Autonomous Engineering Team Runtime) TEST NOW

  • Link: github.com/Agent-Field/SWE-AF · built on AgentField control plane.
  • License (verified from the LICENSE file): Apache-2.0, copyright 2025 AgentField Contributors.
  • Verified repo facts (GitHub, Nov 12, 2026): 311 commits, 48 branches, latest commit Nov 10, 2026 ("Fix the Python image build… build and smoke test"), touching README, docs, Dockerfile, CI and the Python package — active within the last 7 days. Status badge: public beta. Star count was not independently verified in this check, so none is quoted.
  • What it does (simple English): you send one goal ("Add JWT auth") plus a repository; planning agents produce a PRD, architecture (reviewed by a tech-lead agent) and an issue DAG; coders implement issues in parallel in isolated git worktrees; every issue gets dedicated coder → tester → reviewer passes; a middle-loop advisor retries, splits or escalates failed issues; an outer-loop replanner restructures the remaining plan; a merger integrates branches; an integration tester and a verifier check the result against acceptance criteria; the result is a merged branch or a GitHub PR watched through a post-PR CI gate that forbids the fix agent from silencing tests. Checkpointing supports resume_build after crashes.
  • Recent verified change: commits on Nov 9–10, 2026 including "WorkAF build_issue, native plan review and the fence" (Go node) and the Nov 10 build/CI fix. This is an update to an established project, not a new release.
  • Why it matters to a vibe coder: it is the closest open-source shape of Agency OS itself — separate specialist agents, artifacts at every stage, verification against written acceptance criteria, and explicit, severity-rated debt tracking instead of silent scope cuts.
  • Costs (verified status): the software is free (Apache-2.0). Real costs are model API keys (Anthropic, OpenRouter, OpenAI, Google) — the README's own worked example of a 10-issue build cost $19.23 in API spend, and its benchmark build cost ~$6 with MiniMax M2.5 via OpenRouter or ~$20 with haiku-class Claude. A typical build spins up 400–500+ agent instances. Railway one-click hosting is a paid service you do not need locally; a local Docker or host install avoids it. Open source ≠ free model access.
  • Windows compatibility: no native Windows path is documented. The documented install routes are Docker/Compose (works on Windows via Docker Desktop/WSL2), Railway, or a host install with Python 3.12+ and the af CLI via a bash install script (Linux/macOS). One README caveat names WSL2 directly: the Codex runtime's sandbox needs Linux user namespaces, which local Docker on WSL2 may refuse. Windows status: plausible via WSL2/Docker, UNTESTED on this PC.

Honest Gaps

  • SECURITY: the code reviewer touches security in passing, but there is no dedicated security-scanning stage in the pipeline. Verified gap-filler from the same organization, linked in the SWE-AF README: SEC-AF, an AI-native security auditor (multi-agent audits where "every finding [is] proven exploitable", per its own README). Treat as a candidate to verify separately — it has not been featured or tested here.
  • CEO_REVIEW / human approval: no human gate anywhere in the flow; the PR gate is CI-only.
  • RELEASE/deployment: the pipeline ends at a green PR; nothing deploys.
  • PROPOSAL/client artifacts: the PRD is an internal planning artifact, not a client proposal or quote.
  • Governance: no project-state file, no gate engine, no rollback semantics beyond build checkpoints.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: its 16 documented agents (PM, architect, tech lead, sprint planner, coder, QA, reviewer, advisor, replanner, merger, verifier…) mirror Agency OS's own structure — planning, execution and governance agents as a coordinated control stack, not one do-everything prompt.
  • Evidence before advancing: every stage writes artifacts (.artifacts/plan/, .artifacts/execution/, .artifacts/verification/) and the verifier checks acceptance criteria against the PRD — the same "evidence validated before advancing" principle your gate engine enforces.
  • No invented success: the post-PR CI gate's fix agent is explicitly forbidden from silencing tests (no pytest.skip, no xfail, no loosened assertions); when CI stays red, the PR stays open with visible failing checks for a human.
  • Explicit compromise tracking: when scope is relaxed, debt is typed, severity-rated and propagated instead of hidden — directly usable as gate evidence.
  • Compatibility status: plausible, untested. Nothing in the docs shows it reads project-state.json or enforces lifecycle gates, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • Public beta: the project says so itself; expect rough edges and fast change (311 commits, no git tags on the default view — pin the commit you install).
  • Unattended runs cost real money: 400–500+ agent instances per feature build; budget caps exist per loop (max_coding_iterations, max_advisor_invocations, max_replans) — set them deliberately and watch the API bill.
  • Self-reported benchmarks: the 95/100 benchmark and the $19.23 example are the project's own claims, not independently verified here.
  • Autonomous git and GitHub writes: with GH_TOKEN set, it clones, pushes branches and opens PRs. Use a scratch repo and a fine-grained token scoped to that repo only.
  • WSL2 sandbox caveat: the Codex runtime's bubblewrap sandbox may fail on WSL2 ("No permissions to create a new namespace"); the coder then cannot write files. Prefer the Docker or OpenCode runtimes on Windows.
  • No human gate: never wire SWE-AF's PR output past CEO_REVIEW, client acceptance or release — those approvals stay yours, in the gate engine.
  • Windows: no native path documented; WSL2/Docker Desktop only, untested on this PC.

Agency OS Integration Proposal: SWE-AF as the DEVELOPMENT→QA execution engine behind the gate engine

  • Problem solved: Development and QA today are one agent doing both jobs in one context; SWE-AF gives you separate coder, tester, reviewer and verifier agents with artifacts for each.
  • Workflow improved: after your ARCHITECTURE gate passes, hand the approved spec to SWE-AF as the goal; its issue DAG, code branches, test results and acceptance verification come back as gate evidence.
  • Lifecycle point: DEVELOPMENT and QA, feeding the QA and SECURITY gates; the issue-level implement_issue entry point (4–8 LLM calls instead of hundreds) is the cheapest way to delegate one well-scoped issue at a time.
  • Inputs and outputs: an approved spec/goal plus repo in; branches, test results, acceptance-criteria results, typed debt items and (optionally) a PR out.
  • How results are validated: gate_engine.py treats .artifacts/verification/ results and the debt ledger as candidate evidence; a human confirms QA before the gate advances. SWE-AF's own self-reported success is never sufficient evidence on its own.
  • What happens on failure: a failed or partial build returns its branch with success: false and debt items; the gate logs it as not-advanced, and nothing proceeds without human review. No auto-waivers.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). CEO_REVIEW, scope changes, waivers, client acceptance and release stay human — SWE-AF is never wired past them.
  • Smallest safe experiment: today's scratch-repo build; then map its .artifacts/verification/ output onto your QA gate's evidence checklist. Zero changes to Agency OS scripts.

Daily Learning: "accept with debt" — the quiet failure mode of adaptive agents

  • Concept (simple English): SWE-AF's middle loop, when retries are exhausted, can accept an issue with debt instead of failing. That is honest — but it means a build can finish "successfully" while shipping known weaknesses, typed and rated in a debt ledger most people never read.
  • How an AI agent might get it wrong: it reports the build as completed, buries the accepted debt in a log file, or downgrades severity to avoid escalation — a green checkmark over a real compromise.
  • How you recognize the failure: success reports with non-empty debt_items; "completed" outcomes where acceptance criteria were relaxed; debt items that never resurface in later planning.
  • What detects it: your gate engine treating any build with accepted debt as requiring explicit human sign-off before QA advances, and a rule that debt items must be re-raised at CEO_REVIEW until resolved.
