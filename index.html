Start Here (plain English)

The problem: when you hand work to AI agents, the hard part is not generating code — it is running the whole delivery machine: picking which issues agents should even touch, watching each piece of work from "someone asked for it" to "a human reviewed the pull request", and keeping a trustworthy record of what happened and why. Solo agencies usually improvise this in chat scrollback and lose the audit trail.

The solution in today's radar: superplanehq/superplane, an open-source factory platform for "one-shot engineering". It looks at your backlog, picks the issues agents can handle with high confidence, runs them through visible workflows (called Automations) built on a canvas of components — trigger, planning, agent, checks, human approval, source control — and turns each task into a Work Order: a durable, append-only record from draft to success or failure, ending in a pull request. Ambiguous work and judgment calls are deliberately routed back to a human.

The Featured Factory: superplanehq/superplane — backlog in, high-confidence issues selected, agent-built, human-approved, pull requests out INVESTIGATE

  • Link: github.com/superplanehq/superplane — a self-hostable Go + React platform ("open source factory for one-shot engineering"). It turningly calls its unit a Software Factory: a first-class resource that owns Automations (canvas-built workflows) and Work Orders (one durable record per piece of work).
  • License (verified from the LICENSE file): dual-licensed — the repository is Apache 2.0, but files under /ee are under a separate SuperPlane Enterprise Edition License (e.g., custom roles and groups are gated behind an Enterprise license). The core factory engine is Apache 2.0.
  • Verified repo facts (GitHub, Nov 21, 2026): 10.1k stars, 712 forks, 83 contributors, 81 releases (latest: Fleet Manager v0.1.7, Oct 28, 2026), 4,300+ commits, languages 57% Go, 40% TypeScript. A serious, team-scale project — much heavier than yesterday's single-author Claude Code factory.
  • What it does (simple English): it analyzes backlog issues, helps you refine plans, and decides which tasks are safe to delegate to an agent. Each task becomes a Work Order (draft → ready, approved by a human) that flows through Automations: the agent builds, checks verify the result, failures go back to the agent with context, an agent review scores merge confidence, and a pull request lands for human review. Work Order history is append-only: approvals, retries, reopens and outcomes are events that never rewrite earlier history.
  • Verified recent change (last 24–48h, commits of Nov 20, 2026): "feat: Add custom stages to factory lines" (#9438), "fix: Require one human approval for review requests" (#9395, Nov 19), "fix: Enable subscription models in custom automations" (#9472); the docs requirement for one human approval on review requests landed Nov 19. Weekly activity includes a gosec security gate added to CI (Nov 10) and OpenTelemetry upgrade (Nov 18).
  • Why it matters to a vibe coder: it industrializes the two decisions a human adds the most value to — what to build and whether the result is right — while agents do the middle. Work Orders, velocity metrics (human vs factory-authored), and a "Needs attention" queue give a one-person agency the operating picture that normally requires a staff engineer.
  • Costs (real): the engine is Apache 2.0 and self-hostable for free via Docker Compose on one Linux VM or Kubernetes, but open source is not free: you pay for a server, for model tokens (bring-your-own agents and keys; subscription model support added Nov 20), and third-party services are excluded from its tracked cost metric. A hosted SuperPlane Cloud exists (paid plans; team seats and token usage billing appear in its PRDs).
  • Windows compatibility: not direct. Self-hosting targets Linux (Docker Compose, Kubernetes); contributor setup is Docker-based. On Windows the realistic path is WSL2 or a small Linux VM/server. Untested on Windows here.

Honest Gaps

  • PROPOSAL and pricing: no commercial layer; it manages engineering work, not client deals.
  • RELEASE/deployment: the intended output of a Work Order is a pull request; the domain model stops at merge. Deployment is outside the factory.
  • SECURITY: no dedicated security-scan component in the factory workflow; the gosec gate (Nov 10) protects the repo itself, not your projects by default. Pair with an external scanner if you use it.
  • Operations weight: it is a platform (server, database, runners, fleet management), not a repo you clone and run with one command. Self-hosting means Docker Compose on a Linux VM or Kubernetes, running and secured by you.
  • Governance: Work Orders have an explicit lifecycle (draft → ready → successful → unsuccessful) with append-only events, but there is no project-state.json, no Agency OS gate engine, and no rollback-protection machinery in the Agency OS sense. Its approvals complement gate_engine.py, never replace it.
  • Biggest gap for a client-facing vibe coder: no release/deploy stage and no proposal layer — both stay manual in Agency OS, and hosting the platform itself is a real, ongoing cost.

Why It Fits Agency OS

  • Work Orders are living project state: each piece of work has a durable, chronological, append-only record — conversations, decisions, approvals and steering instructions are events, and retries/reopens append rather than overwrite. That is the same mindset as a project-state file that any run can stop, resume and audit.
  • Explicit lifecycle states with approval: a Work Order stays draft until approved, then becomes ready; success and failure are explicit declared outcomes, never inferred from PR state — mirroring Agency OS evidence-validated transitions.
  • Agents do not own the decisions that matter: the factory routes ambiguous work and judgment calls back to people; docs landed Nov 19, 2026 requiring one human approval for review requests. Commercial decisions stay out of agent hands by design.
  • Evidence beside the PR: checks results, failures sent back with actionable context, and an agent merge-confidence assessment are kept so "your team can make the final decision with evidence" — not vibes.
  • Specialized components, orchestrated: Automations are composed from narrow components (trigger, planning, agent, checks, human approval, source control) on a visible canvas — the same orchestrator-plus-specialists separation Agency OS assumes.
  • Compatibility status: plausible, untested. Nothing shows SuperPlane reading project-state.json or enforcing Agency OS transitions; its artifacts would enter Agency OS governance as candidate evidence only, validated before any gate advance.

Limitations, Risks & Human Review

  • It is a platform, not a plugin: adopting it means running a server (and runners) reliably, patching it, and backing it up. For a one-person agency that is a real ongoing commitment, versus yesterday's prompt-file factories.
  • Dual license details: the core is Apache 2.0, but /ee is under an Enterprise Edition License; features like custom roles/groups sit behind it. Check which features you actually assume before building on it.
  • Windows: self-hosting targets Linux; use WSL2 or a small VPS. Untested on Windows here — verify before promising anything to a client.
  • Model costs: bring your own agents and keys; subscription model support was only enabled Nov 20, 2026. Token and compute costs are tracked for factory work but third-party charges are excluded — budget separately.
  • Unattended-run safety: any Automation that creates PRs on real repositories can churn tokens fast; keep small bugs/docs fixes as first runs, use merge=approve-style human confirmation where offered, and keep your machine/approvals in the loop before enabling scheduled laps.
  • Human review points, honestly: approvals are explicit Work Order events, but the product model doc is still a Draft — some orchestration details are "not yet decided". Treat its governance narrative as evolving software, not settled law.

Agency OS Integration Proposal: Work Order events as gate evidence for DEVELOPMENT → QA (not a new engine)

  • Problem solved: Agency OS validates evidence before advancing, but building the QC/review evidence for heavier Work Orders manually is toil. SuperPlane already produces a checkable, append-only event record per piece of work — approval events, check results, failure-and-fix loops, merge-confidence assessment.
  • Workflow improved: the DEVELOPMENT → QA and SECURITY → CEO_REVIEW handoffs: export a Work Order's event chronology (and its approval events) as a markdown/JSON artifact and attach it as gate evidence, so the QA gate sees the full correction history, not just the final state.
  • Lifecycle point: QA and CEO_REVIEW gate inputs. The event export rides beside the evidence, never instead of it.
  • How results are validated: gate_engine.py still validates artifacts and enforces transitions; the Work Order export is candidate evidence validated like any other. No governance, gate engine or project-state.json logic changes.
  • What happens on failure: if the export is missing or unverifiable, the gate blocks exactly as it does today — no new failure mode.
  • Gate or human approval: human approvals remain human; the export only makes their history auditable. It never advances a gate by itself.
  • Smallest safe experiment: run one Work Order on a scratch repo, export its event chronology, and see if reading it is genuinely faster than reading the PR diff and comments. If yes, template the export into the QA gate checklist; if not, discard — nothing in Agency OS changed.

Daily Learning: work-order events as an audit backbone (append-only system of record)

  • Concept (simple English): SuperPlane makes the record of a piece of work append-only: approvals, retries, reopens and outcomes add events and never rewrite earlier ones. The current state may be cached for speed, but the history must always be explainable from the event log. That is the same discipline as an immutable audit log — and a counter to "agents quietly retelling what happened".
  • How an AI agent might get it wrong: state that lives in one mutable field invites agents (or well-meaning humans) to overwrite it: a Work Order marked "successful" without a trace of which check failed first and who approved the fix. Once the history is rewritten, no one — and no gate — can prove the claims.
  • How you recognize the failure: a report says "approved and verified" but the underlying record cannot show the sequence of events that produced the approval, or earlier failed attempts have vanished from the story.
  • What detects it: keep every gate decision and retry in an append-only log (files, commits or journal), validate current state against the log, and treat any unexplained state change as a failed gate. Evidence must always be reconstructible from the events.
