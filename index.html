Start Here (plain English)

The problem: when you step away from the keyboard, your coding agents either stop working (safe, but you become the factory's bottleneck) or keep going without you (productive, but who decides what is allowed to merge?). Most agent frameworks make you choose between the two. For a one-person agency, the real answer is a factory that calls you — like a factory andon light — only when a decision exists that only a human can make.

The solution in today's radar: mitaku/andon, "a one-person software factory." A file-based issue ledger (kanban) feeds AI agents that implement, review and merge issues; a rules-based gate decides what can merge without you; and a light turns on for exactly five kinds of human decisions — what to build, how users experience it, promises to the outside, irreversible risks, and changes to the line itself. Everything else runs with the lights on for the agents, off for you.

The Featured Factory: mitaku/andon — a one-person software factory INVESTIGATE (maturity)

  • Link: github.com/mitaku/andon — a Go package, contract documents and a container image for running a software "line" with AI coding agents, built by its author (mitaku) for his own solo use first.
  • License (verified on GitHub, Nov 23, 2026): Apache License 2.0 (LICENSE file present and confirmed on the repository's license page).
  • Verified repo facts: 205 stars, Go, 515 commits, 14 tags, public in this form since Nov 9, 2026. Latest commits dated today, Nov 23, 2026 (#520 triage/retro ledger keys, #521 owner questions via andon issue ask --new, #522 verification-map gate, #517 dispatcher green-mark sync).
  • What it is (simple English): one long-lived Docker container, a "cell," is set up per trust boundary (per client, per hobby). Inside, a coordinating agent (the Chief of Staff) reads a file-based issue ledger, starts one worker agent per issue in its own git worktree, asks a reviewer agent of a different model family to review the pull request, and lets a rules-based gate decide what can merge without a person. The cell's own root directory is itself a git repository: project instructions, skills, wiki and settings are versioned and movable, while the ledger lives with the cell outside git.
  • Classification: new public project (public since Nov 9, 2026; a predecessor private factory existed — its history is traceable in "Y-number" ledger references). Tags exist, but the README states there are no releases with compatibility promises yet; the status is explicitly "experimental."
  • Verified recent change (last 7 days): multiple commits every day through Nov 23, 2026 — gate delegation handling and dispatcher state alignment (#517), decision provenance (decidedBy marks, #510/#512), a verify-andon skill gate (#522), and agent write access to PR conversations closed off by configuration and rules (#514). CI runs Go tests, shell tests and even a tests/public.sh secret-pattern check on every pull request.
  • Why it matters to a vibe coder: it is opinionated exactly where you are weakest when working alone: it writes down (as JSON Schema-checked contracts) which decisions a human must make, what evidence each gate reads, and what the agents may never decide. This is a governance design, not just a runner.
  • Costs (real): the factory is Apache-2.0, but the agent CLIs it embeds in the image (Claude Code, Codex) run on their own subscriptions or API keys. Docker itself is free; on Windows, Docker Desktop's licensing for larger commercial use should be checked separately. The image ships Playwright with a pre-installed browser for black-box verification — included, not extra.
  • Windows compatibility: the host needs only Docker and bash, so WSL2 is the realistic path on Windows; the cell container itself is Linux. Untested on Windows here — assume nothing for client machines. Cell timezone defaults to Asia/Tokyo (configurable via CELL_TZ).
  • Honest caveat noted up front: most project documents are in Japanese, with an English summary in the README; the interface changes without notice; and the project does not accept external pull requests right now.

Honest Gaps

  • PROPOSAL and pricing: absent. Commercial quotes stay in Agency OS, as they should.
  • RELEASE/deployment: the ledger's line ends at a confirmed merge; staging and deployment are yours to run.
  • Product-level security scanning: the security model protects the cell (container boundary, pinned tools, secret patterns, closed PR write access). There is no SAST or dependency-scanning stage for the code it writes; keep Agency OS's security stage and an external scanner.
  • Language and reachability: documentation is Japanese-first; an English summary and English kanban CLI docs exist, but expect to read Japanese for depth (design.md, ADRs, contract).
  • Governance maturity: a one-person project, explicitly experimental, interfaces change without notice, no releases with compatibility promises, no external PRs accepted. There is no Agency OS-style gate engine or project-state.json; its gate conditions table complements gate_engine.py, never replaces it.
  • Model dependence: the design assumes Claude Code and Codex CLIs at specific versions in the image; other agent runtimes are not described.

Why It Fits Agency OS

  • Human decisions are enumerated, not implied: exactly five decision categories (what to build, user experience, external promises, irreversible risks, changes to the line) are constitutionally reserved for the human — the same discipline Agency OS enforces at CEO_REVIEW, scope changes and release.
  • Evidence and provenance over claims: every answer to a kanban question carries a decidedBy mark (#510/#512); a decision without a mark and an owner is counted as needing the owner (#519), so nothing advances on an agent's say-so.
  • Rules-based gates, not self-assessment: what merges without a person is decided by a conditions table (gate.json), and the workflow state machine rejects transitions not defined in process/states/issue.yaml — the same "outside-the-agent enforcement" pattern as gate_engine.py.
  • Machine-readable contracts: promises between components live in JSON Schema, validated by tests — artifacts a gate can check, not vibes in a prompt.
  • Specialized agents, orchestrated: Chief of Staff, per-issue workers, cross-model reviewers and a non-judging dispatcher — the orchestrator-plus-specialists pattern Agency OS assumes, with reviewers deliberately from a different model family to avoid common-mode failure.
  • Living state: the kanban ledger, process definitions and decisions ledger are the living project state — the ledger kept outside git precisely because it is a run log, while rules and structure stay versioned.
  • Compatibility status: plausible, untested. Nothing shows andon reading project-state.json or enforcing Agency OS transitions; its artifacts would enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • Experimental maturity: used by one person, built for one person; expect rough edges, silent interface changes and no upgrade guarantees. Do not build a client deliverable on it yet.
  • Japanese-first docs: if you do not read Japanese, your verify-what-you-adopt budget is higher than the README suggests.
  • Model costs: Claude Code and Codex subscriptions apply per session; unattended loops can burn tokens. Andon's own governance model (bounded decisions, human-only categories) limits scope but not spend — set your own budget discipline on day one.
  • Unattended-run safety: the design's answer is selective autonomy: machines stop what machines can decide. Still, review the gate conditions before trusting any merge that "passed without a person," and keep the five decision categories untouched by delegation except one deliberate per-project scope, never including "what to build."
  • Windows: Docker + bash on the host means WSL2; container is Linux; cell default timezone is Asia/Tokyo (configure CELL_TZ). Untested on Windows here.
  • Human review points: the andon light (owner summons), gate conditions changes, line changes and the five decision categories. Do not delegate those, ever.

Agency OS Integration Proposal: adopt andon's "five decisions only humans make" as named categories in the gate engine metadata (not a new engine)

  • Problem solved: Agency OS requires human approval for commercial decisions, scope changes, client acceptance and release — but those categories live in policy/guidance, not as machine-checkable metadata attached to gate transitions. andon shows they can be a first-class, delegable-per-project, schema-validated surface with provenance marks.
  • Workflow improved: OWNER_DECISION tagging inside the existing gate engine: before any transition requiring human approval, the gate emits which named category applies (and whether the project's delegation table covers it), and the approval record stores a decidedBy-style provenance mark.
  • Lifecycle point: CEO_REVIEW and RELEASE gates, plus the LEAD gate's intake rule "what to build is never delegated."
  • How results are validated: gate_engine.py still validates artifacts and enforces transitions; the category table is candidate evidence like any other. No governance, gate engine or project-state.json logic changes.
  • What happens on failure: if an approval lacks a decision-category or provenance mark, the gate blocks exactly as it does today.
  • Smallest safe experiment: take one recent Agency OS CEO_REVIEW approval and write its record with a decision category plus decidedBy: <owner>. If any past approval cannot be categorized in five or fewer named buckets, your approval rules are vaguer than andon's — and that is the finding to fix.

Daily Learning: the selective dark factory — deciding who decides

  • Concept (simple English): a "dark factory" runs with no person on the floor. andon's twist is selective: machines stop what machines can decide (tests, gate conditions), language models handle what needs judgment (implementation, review), and a person sees only what is left — five named decision kinds. Autonomy is not a dial from 0 to 100; it is a division of decision rights, written down.
  • How an AI agent might get it wrong: with fuzzy authority, an agent drifts one way or the other: it either escalates nothing (it "decides" scope, external promises or risky changes quietly and merges them) or escalates everything (it interrupts you for trivia, and you start rubber-stamping approvals without reading them).
  • How you recognize the failure: check provenance: an approval record without a decision category or decidedBy mark; a merge that nobody can point to the rule that permitted it; or your own queue full of approvals you click through on autopilot.
  • What detects it: enumerate the human-only decision kinds for your own agency (like andon's five), store them as gate metadata, require a provenance mark on every approval, and treat "escalated without a category" or "merged without a rule" as gate failures. In Agency OS, gate_engine.py is already the outside-the-agent enforcer — the categories just make it sharper.
