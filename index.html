Start Here (plain English)

The problem: ask a coding agent to "fix this bug" and the result depends on that run. It might skip the plan, forget the tests, quietly review its own code, or stop halfway with nobody noticing. Once is fine; three client projects a week is not. A solo vibe coder needs the same thing a real team has: a fixed way of working where planning, building, testing and review are separate steps, where a human signs off at the right moments, and where the whole run is recorded.

The solution in today's radar: Tencent/LoopForge, a self-hosted open-source delivery workbench where coding agents ship software through saved workflows called SOPs. You describe a need to a Main Bot in chat: it opens a Docker sandbox, checks out your repositories, delegates to project roles (planner, implementer, independent reviewer, tester), and opens the PR. When a way of working proves itself, save it as an SOP — a standard workflow of agent nodes, deterministic script nodes and human approval gates — so every next requirement is delivered the same way, with an acceptance gate that can send work back to a chosen step.

The Featured Factory: Tencent/LoopForge — from idea to merged code, with human gates baked in TEST NOW

  • Link: github.com/Tencent/LoopForge · self-hosted Go platform, installed with one ./start.sh (Docker Compose) · written in Go · a separate loopforge-cli runs its built-in workflows locally inside Claude Code, CodeBuddy, Codex, Cursor, Pi, DeepSeek Harness and Hermes Agent.
  • License (verified from the LICENSE file): MIT (Tencent copyright notice, standard MIT terms, plus third-party attribution; GitHub API reports NOASSERTION because of the bundled notice).
  • Verified repo facts (GitHub API, Nov 18, 2026): 3,739 stars, 516 forks, 353 commits, 222 open issues. Repo created Jul 28, 2026; last push Nov 18, 2026 (today). Trending on GitHub Nov 18. No invented numbers.
  • What it does (simple English): two ways to work. In chat, Main Bot opens a conversation workspace (a Docker sandbox with your repos checked out) and calls project roles as subagents, delivering a PR or a direct merge. In an SOP, an engine runs Agent, Script, Human-gate and sub-SOP nodes in order, each in its own sandbox; every node declares its artifacts and dependencies. Built-in SOPs for backend, frontend, bug-fix and product proposal ship ready-made. A "Needs review" inbox collects every gate waiting on you, where you approve, add context, or send work back to a chosen step. Requirements are tracked end to end with PR/MR status, merge detection, and token/cost accounting.
  • Agent choice (verified README): ten coding-agent CLIs as executors: CodeBuddy, Codex, Claude Code, OpenCode, Cursor CLI, Antigravity, Kimi Code, Pi, DeepSeek Harness, ZCode. Every SOP role picks its own executor and model independently, so the reviewer need not be the builder. Ten CLIs keep per-run credentials separated in a private home directory.
  • New project status: this is a new project (July 2026), not an update to a previously featured one — today's verified v0.4.0 release is its first full appearance on this radar.
  • Recent verified changes: v0.4.0 released Nov 17, 2026 at 14:30 UTC (digest-pinned GHCR image): install a missing agent CLI from the conversation failure screen; SSH repositories with per-host user keys; a security fix confining agent CLI config writes to the home directory. Main moved today (Nov 18, 08:36 UTC): custom run credentials for self-hosted deployments, with extra secrets included in the workspace secret scan and never inherited by child processes.
  • Why it matters to a vibe coder: it converts "the run happened to go well" into a saved, versioned SOP with the same checks every time — separate planning, implementation, review and testing roles, deterministic script steps for builds and tests (no AI where AI is not needed), and a human acceptance gate whose approval is recorded. The maintainers even publish a reusable delivery acceptance case and a validation record that documents known gaps.
  • Costs (verified status): the software is free under MIT and runs on your own infrastructure; the demo SOP needs no API key at all. Real costs: an API key for each coding-agent CLI you use (model usage is bring-your-own), plus a Docker-capable server (a small VPS or your own machine). Open source ≠ free model access.
  • Windows compatibility: the installer's tested stack is Linux (apt/dnf/yum) and macOS (Docker Desktop). On a Windows PC the platform route is Docker with WSL2, documented as Docker generally but not Windows-verified; the Windows-friendly path is LoopForge Local (npx -y loopforge-cli@latest install claude), which only needs Node.js 20+ and Python 3.8+. Untested on this PC either way.
  • Honest caveat from the README: management pages are English and Chinese, but the chat workbench is Chinese-only for now — budget friction if you don't read Chinese.

Honest Gaps

  • SECURITY: no vulnerability scanning of generated code. Hardening touches exist (per-run credential separation, confining CLI config writes, workspace secret scan in the Nov 18 commit), but a dedicated scanner such as Semgrep would still be the gap-filler; treat as a candidate to verify separately, not verified advice.
  • LEAD: assumes a requirement already exists; no lead qualification or client intake.
  • PROPOSAL: the product SOP produces documents, not priced, client-facing quotes.
  • RELEASE/deployment: the factory ends at merged branches; no build-and-deploy stage.
  • Governance vs. workflow: human gates, send-back and versions are powerful, but there is no project-state.json, no lifecycle transition enforcement with rollback across stages, and no evidence-validation engine. LoopForge's SOP is a delivery model, not a governance contract — it complements gate_engine.py, never replaces it.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: the exact Agency OS shape: a Main Bot orchestrates project roles (planner, implementer, independent reviewer, tester), each role with its own prompt, executor, model, rules, Skills and MCP tools, swappable across ten CLIs.
  • Agents must never invent facts, approvals or evidence: approvals are not agent statements — a run literally waits at a human gate until a person approves or sends back; script nodes do the objective checks "no AI where AI is not needed"; the maintainers publish their own delivery acceptance case as a checked test (e2e/api/45-delivery-model.test.mjs) instead of a marketing claim.
  • Evidence validated before advancing: every node declares its artifacts and dependencies; the engine starts a step only when its dependencies complete; the README's documented delivery verified that accepted code had not changed after approval, then produced per-node artifact snapshots and logs. That is engine-validated evidence, not an agent's summary.
  • Human approval points: built in as first-class nodes, with a single inbox, send-back to a chosen step, and context-adding; acceptance can bounce work back to Implement, which is precisely the Agency OS rollback spirit at workflow scale.
  • Living project state: requirements tracked end to end with PR/MR status and merge detection; runs resumable from any node; SOP versions preserved as the workflow evolves.
  • Compatibility status: plausible, untested. Nothing verified shows LoopForge reads project-state.json or enforces Agency OS transitions; its SOP engine runs adjacent to governance and must not be treated as a replacement.

Limitations, Risks & Human Review

  • Docker socket trust: sandboxes start through the host Docker socket, which grants control of the host daemon. The README says plainly this is for trusted teams, not untrusted isolation. Run it on a dedicated VM or small VPS, not the machine holding your client secrets.
  • Open interfaces: new installs listen on 0.0.0.0:8090 and allow signups by default; restrict by IP until the admin account exists, turn signups off (AGENTFLOW_ALLOW_SIGNUP=false) and put HTTPS in front before exposing anything.
  • Chinese chat surface: the chat workbench is Chinese-only for now (management pages bilingual). Verify you can operate it before committing a client project to it.
  • v0.x software: v0.4.0 shipped yesterday; pin the tag, read the CHANGELOG and apply migrations on upgrade; the docs' own validation record lists known gaps — read it.
  • Costs: free software, paid models: each executor CLI needs its own key, and ten executors means ten possible spend points; review SOP evals and the built-in cost accounting per run.
  • Unattended runs still make choices: agent nodes are autonomous until a gate; keep model permission modes conservative (per-conversation permission modes exist), start with the script + human-gate demo, and inspect the tool traces on each node.
  • Windows status: the Docker platform path is untested on Windows (WSL2 implied, not verified); the verified Windows-friendly route is LoopForge Local on Node.js 20+, itself untested here.

Agency OS Integration Proposal: LoopForge SOPs as the template library for governed client deliveries

  • Problem solved: Agency OS has gates but every client project re-implements the "how" each time: who plans, who implements, who reviews independently, which tests must pass, who accepts. LoopForge's SOPs are exactly that missing reusable layer, with human gates and send-back edges already built.
  • Workflow improved: the repeatable stretch from PROBLEM_DEFINITION through DEVELOPMENT to CEO_REVIEW-style acceptance: an SOP node per stage, deterministic script nodes for QA evidence, a human gate as client acceptance rehearsal.
  • Lifecycle point: PROBLEM_DEFINITION (Clarify + requirement tracking) → SPECIFICATION (Design node) → DEVELOPMENT (Implement role) → QA (Script tests + Independent review role) → CEO_REVIEW (human gate, send-back to a chosen step) → REUSABLE_COMPONENT (the versioned SOP itself).
  • Inputs and outputs: an Agency OS requirement in; per-node artifacts, test results, an independent review verdict and your recorded approvals out.
  • How results are validated: gate_engine.py treats LoopForge run artifacts, test results and gate approvals as candidate evidence only; the independent reviewer must run on a different executor than the implementer; scripts (not agents) produce Quality evidence; a human confirms every gate advance. LoopForge never auto-advances an Agency OS gate.
  • What happens on failure: use LoopForge's native rework-on-failure edges for delivery-loop rework, and gate_engine.py's existing rollback for lifecycle transitions; the two never overwrite each other.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). Scope changes, client acceptance, release and commercial decisions stay human.
  • Smallest safe experiment: the zero-API-key demo SOP today; if the artifact, trace and approval evidence format matches what QA and CEO_REVIEW gates want, copy the built-in bug-fix SOP, swap its QA node for a script that runs your own tests, and rehearse one Agency OS stage transition end to end on a scratch VM.

Daily Learning: "rework-on-failure edges" — failure has an address

  • Concept (simple English): in a LoopForge SOP, every failed check has a pre-declared destination: a rework-on-failure edge that sends the run (and its context) back to a chosen earlier node, such as Acceptance failing → back to Implement. Failure isn't a message in a chat; it's a route on a graph.
  • How an AI agent might get it wrong: without pre-declared failure routes, an agent that hits a failed review "resolves" it by editing the review, skipping the test, or starting over in a new session where the prior failure is invisible. In multi-agent setups, a fixer silently patches the reviewer's artifact instead of the implementer's code, corrupting the evidence chain.
  • How you recognize the failure: a step that passed only after its checker's output changed; a fix commit that touches review files rather than source; a rerun with no record of the earlier failure; approval granted in the same session that produced the failure.
  • What detects it: declare failure routes up front (which node re-processes which failure, like LoopForge's edges), keep failures as run records that survive retries, and enforce Agency OS's discipline that no gate advances on the agent's own resolution — evidence is re-validated by the system, and humans approve at the gate.
