Start Here (plain English)

The problem: you are one person. Even with AI agents, one client project means juggling specs, reviews, fixes and merges — and agents drift: they say "done" before the work actually passes review. You need a system where nothing advances until a defined success criterion is met, without babysitting every step.

The solution in today's radar: nexu-io/looper runs a small AI dev team on your own machine. Label a GitHub issue looper:plan and specialized agents — Planner → Reviewer ↔ Fixer → Worker — loop, each against its own exit condition (spec reviewable, review clean, threads resolved, checks pass), until a PR is ready for your human merge. GitHub itself is the workflow state: labels gate every transition, so you can pause, intervene, or take over at any boundary. Local, inspectable, stoppable — no hosted control plane.

The Featured Factory: nexu-io/looper INVESTIGATE

  • Link: github.com/nexu-io/looper
  • What it is (simple English): an autonomous AI dev team for your GitHub/Forgejo repos — plan, review, fix and ship PRs, on a loop. Two binaries: looperd (local background daemon that polls the forge, runs loops, manages git worktrees) and looper (CLI for ps, logs, stop). Every loop runs in its own isolated git worktree, so agents work in parallel without stepping on each other.
  • Four loops, four success criteria (no fixed step counts, just goals): 🧭 Planner loops until the spec is reviewable (spec PR open, labeled looper:spec-reviewing); 🔍 Reviewer loops until the PR meets the bar (no actionable threads, clean review); 🔧 Fixer loops until reviewer threads are handled; 🚢 Worker loops until the PR is ready for merge (implements the looper:spec-ready spec PR, runs checks, iterates on its own output).
  • What changed recently and when (VERIFIED): latest commit Oct 28, 2026 — "feat: add opt-in reviewer maintainability skill (#684)"; latest release v0.16.2 on Oct 24, 2026, GPG-verified signature, containing reviewer follow-up sweep fixes (#680–#682). A mature, continuously updating project (445 commits, 81 branches, 73 tags), not a brand-new repo.
  • Why it matters to a vibe coder: it is a working reference implementation of Agency OS's core idea — specialized roles with success criteria, transitions gated on machine-readable state (GitHub labels), and human merge as the hard stop. Start from an issue, not a prompt: the issue is the requirement; the PR is the evidence.
  • License & costs (verified): MIT License (verified in the repo LICENSE, added Apr 29, 2026). Looper itself is free and has no subscription or hosted control plane. Real cost: your agent CLI's model usage — pluggable backends are opencode, claude-code, codex, cursor-cli, grok-build, pi, omp (bring your own model, local models possible). Open source ≠ free model access.
  • Windows compatibility & install: ⚠️ no Windows binary — official install script covers macOS (darwin-arm64) and Linux (linux-amd64/arm64) only. Building from Go source or running under WSL2 is plausible — untested. This is why the verdict is INVESTIGATE, not TEST NOW.
  • Verdict: INVESTIGATE — the design pattern is immediately adoptable; the runtime needs WSL2 on Windows.

Honest Gaps

  • No security stage — no scanning, no secret detection, no dependency auditing. External filler for the biggest gap: gitleaks (MIT; latest verified release v8.30.1) for secret detection.
  • No architecture, deployment, or client/business stages (LEAD→PROPOSAL, client acceptance) — Agency OS keeps those.
  • No Windows binary — WSL2 or source build, untested here.
  • Governance lives in GitHub labels — it complements gate_engine.py, never replaces it; Agency OS's project-state.json stays authoritative.

Why It Fits Agency OS

  • "The forge is the source of truth" ≈ Agency OS's authoritative project state — issues, PRs, labels and reviews ARE the workflow, no hidden task tracker.
  • Label-gated transitions ≈ the gate engine: no transition without the right state marker; you can pause, intervene or take over at any boundary.
  • Each loop has an explicit exit condition ≈ evidence before advancing — the agent cannot declare done early.
  • Human merge is mandatory ≈ Agency OS human approval for release; HITL escalation ≈ BLOCKED states.
  • Local, inspectable, stoppable — looper ps / logs / stop; no hosted control plane, matching the one-person, own-your-stack model.
  • Agency OS compatibility: plausible — untested (no run evidence yet, especially on Windows).

Limitations, Risks & Human Review

  • Unattended agents pushing code is a real risk: use a scratch repo first; keep opt-in reviewer auto-merge OFF; never register client repos before trust is earned.
  • Token cost: loops run until criteria are met — a struggling loop can consume a lot of model budget; monitor with looper logs.
  • Pre-0.17 churn: pin a release; the project ships frequent fixes (v0.16.0–v0.16.2 within October).
  • Safety history to read before running: the repo has explicit safety commits ("safety floor — one admission state and stop unsafe recovery PID", Jul 2026) — read docs/installation.md first.
  • Windows is not the documented path — WSL2 is a workaround; verify everything before relying on it.

Agency OS Integration Proposal: label-gated, spec-first handoffs as gate evidence

  • Problem solved: the dev agent starts coding before a reviewable spec exists, and QA claims "done" without a clean-review artifact.
  • Workflow/agent improved: the PROBLEM_DEFINITION → SPECIFICATION → DEVELOPMENT → QA handoff, feeding — never replacing — gate_engine.py.
  • Lifecycle stage: SPECIFICATION and QA gates.
  • Inputs: a GitHub issue. Outputs: a spec PR with the ready label + a clean review (zero actionable threads), stored as gate evidence.
  • How results are validated: the gate advances only when the spec PR carries the ready label AND the review shows no actionable threads; the orchestrator mirrors this into project-state.json, which remains authoritative.
  • What happens on failure: no label or open threads → gate stays BLOCKED; no advancement, no waivers without human approval (governance unchanged).
  • Gate or human approval? Neither changes — this only defines a stricter evidence format the existing gates can consume.
  • Smallest safe experiment: one scratch repo, one trivial issue, observe the full planner→worker cycle end to end, human-merge at the end, and compare the artifacts against what your current spec/QA stages produce.

Daily Learning: success-criteria loops

  • Concept (simple English): instead of telling an agent "do X in 10 steps," give it an exit condition ("done = spec PR open and reviewable") and let it loop. The state, not the step count, defines done.
  • How an AI agent might get it wrong: it declares success early — opens an empty PR, or claims tests pass without running them.
  • How you recognize the failure: the state advanced but the evidence artifact (reviewable spec, clean review, green checks) is missing or fabricated.
  • What detects it: Looper's label gates (state cannot advance without the PR and label); in Agency OS, gate_engine.py and prepush_release_check.ps1 catch the same failure class.
