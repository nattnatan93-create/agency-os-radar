Start Here (plain English)

The problem: one coding agent can do a task, but a real project needs many: split the work, give each piece its own branch so nothing collides, follow every change through CI, review and merge, and fix the failures. Run agents in parallel by hand and you spend your day as a dispatcher: which branch is whose, which PR is blocked on CI, which review comment went unanswered.

The solution in today's radar: Orchestrator.inc, an open-source desktop workspace that runs a fleet of coding agents from task to merged PR. Every task gets its own agent, branch and git worktree; an orchestrator agent plans the work and starts a worker per piece; failed checks, review comments and merge conflicts go back to the worker that owns the branch until the PR is approved; and a board sorts sessions into lanes so whatever needs you is on top. Your code stays on your machine, and you can steer the whole fleet from your phone.

The Featured Factory: Orchestrator.inc — a fleet of coding agents, from task to merged PR TEST NOW

  • Link: github.com/OrchestratorInc/agent-orchestrator · desktop app (macOS, Windows, Linux) + a local daemon · site: orchestrator.inc.
  • License (verified from the repo's LICENSE and sidebar): Apache License 2.0 for the whole repository.
  • Verified repo facts (GitHub, Nov 17, 2026): 14.8k stars, 2.0k forks, 4,264 commits, English plus 8 translated locales. No invented numbers: these are the sidebar values as shown today.
  • What it does (simple English): you tell a project's main agent what you want built. It plans the work, starts a worker for each piece in its own worktree, and comes back only when something needs you. Every session sorts itself into lanes on one board, driven by the agent, its PR, CI and reviews. Failed checks, review comments and conflicts are routed back to the worker that owns the branch until the PR is approved, and a reviewer agent can read every PR before a person does. Each worker also gets a browser to preview and test its app.
  • Agent choice: pick the agent and model per task, from a verified README matrix of 35+ coding agents: Claude Code, Codex, Cursor, opencode, Aider, GitHub Copilot, Gemini CLI, Goose, Cline, OpenHands, Devin and many more. Worker, chat and reviewer support differ by agent.
  • Recent verified changes: stable v0.15.3 released Nov 16, 2026 at 16:30 UTC (signed): PR details, actions, comments and activity in the session inspector; persisted lifecycle and respawn records; provider keys configurable across harnesses; worktree files restored when rolling back a turn; a reviewer-effort picker; reviewing someone else's PR with automatic fixing off; and a subagents panel that shows subagents as a team. Main was promoted to stable on Nov 16, and signed nightlies landed Nov 16 and Nov 17 (latest 06:10 UTC: stop active TUI turns without killing sessions, and an Open Interpreter Rust TUI integration). This is an actively developed project with daily builds, not a new one.
  • Why it matters to a vibe coder: it removes the dispatching job from solo parallel-agent work: branches can't collide (one worktree per task), CI failures self-route to the owning worker, a reviewer agent pre-reads PRs, and a board shows only what needs you. Push alerts on your phone ask you when an agent has a question or needs approval, so unattended work pauses at real decision points instead of guessing.
  • Costs (verified status): the software is free under Apache-2.0; the desktop app runs a local daemon and your code stays on your machine. Real costs: the subscriptions of the coding agents you run (Claude Code, Codex, etc.) and their token spend, which parallel workers multiply. Optional Cloud Agents run workers in hosted workspaces; Cloud pricing details were not verified today. Open source ≠ free model access.
  • Windows compatibility: a native Windows installer (agent-orchestrator-win32-x64.exe) is listed in the README's install table for macOS (Apple silicon/Intel), Windows and Linux (AppImage, deb, rpm). Verified as shipped; UNTESTED on this PC.
  • Telemetry: the README discloses limited usage telemetry (installation ID and GitHub username; never code, prompts, conversations or credentials), with a documented off switch in Settings that covers desktop, daemon and paired phone.

Honest Gaps

  • SECURITY: no vulnerability scanning of generated code at all. A dedicated scanner such as Semgrep is the classic gap-filler; treat as a candidate to verify separately, not as verified advice.
  • PROPOSAL / SPECIFICATION: the orchestrator plans from your chat instruction; there is no formal spec, proposal or client-facing artifact to gate on.
  • RELEASE/deployment: the factory ends at merged PRs; nothing builds or deploys a release.
  • LEAD / DISCOVERY: assumes you arrive with a project to build; no lead qualification.
  • Gate engine: no project-state file, no lifecycle transition enforcement, no rollback engine. Its review verdicts, CI results and your approvals are raw material for gate evidence, not the gates themselves.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: the exact Agency OS shape, built in: a main agent plans, spawns a worker per piece, and a reviewer agent reads every PR; workers are even swappable between 35+ coding agents per task.
  • Agents must never invent facts or approvals: a PR is not done until CI passes and review approves; failures are routed back to the owning worker by the system, not by an agent's claim; the reviewer-effort picker and "review with automatic fixing off" keep review separable from the builder.
  • Evidence validated before advancing: the board's lanes are derived from real system state (agent, PR, CI, reviews), so what you see is recorded status, not an agent's summary. PR details, actions and comments are inspectable in the session inspector.
  • Human approval points: push alerts fire when an agent has a question or needs approval; you approve from phone or desktop; the maintainers even ask that bug reports come from a human account, with agent-gathered evidence attached as reviewed attachments.
  • Living state: lifecycle and respawn records persist for app and daemon (v0.15.3), and every past session is searchable — a durable record of who did what.
  • Compatibility status: plausible, untested. Nothing in the docs shows Orchestrator.inc reads project-state.json or enforces Agency OS lifecycle transitions, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • Parallel workers multiply token spend: every task runs its own agent on your subscriptions; start with one small project and watch usage before widening.
  • v0.x software with daily nightlies: the stable channel exists (promoted Nov 16) but the version is 0.15.3; pin stable, expect churn, and read each release note before updating.
  • Unattended runs still make choices: workers fix CI and answer review comments autonomously until approval; keep the scoped-permission rules of each coding agent tight and the "needs you" alerts on.
  • Telemetry is opt-out, not opt-in: limited usage telemetry (installation ID, GitHub username) is on by default; turn it off in Settings if you want a fully silent setup.
  • Windows installer is verified as shipped but untested here: budget time for first-run friction and agent CLI setup on Windows.
  • Cloud Agents are a separate surface: hosted workspaces keep running with your laptop closed, but that puts code in someone else's infrastructure; pricing was not verified today.

  • Problem solved: Agency OS specifies and gates well, but running several builders in parallel by hand is the daily bottleneck: branch collisions, unowned CI failures, PRs waiting on reviews nobody tracks. Daily Learning: "self-routing failures" — the system, not the agent, decides who fixes what

  • Concept (simple English): in Orchestrator.inc, when CI fails or a review comment lands, the system routes it back to the worker that owns that branch, and the PR stays unapproved until it passes. Ownership is structural: one task, one agent, one worktree, one PR.
  • How an AI agent might get it wrong: in a shared-branch setup, a builder notices another task's failing CI, "helpfully" fixes it on its own branch, and now one PR mixes two changes, the wrong agent owns the fix, and review cannot tell what happened. In a single-agent setup, the agent declares the failure "minor" and ships anyway.
  • How you recognize the failure: a PR whose diff covers two unrelated tasks; fixes appearing on branches that never failed; "minor, merging anyway" language in a summary with no recorded check rerun.
  • What detects it: a gate rule that every fix must land on the branch that owns the failure, and that no advance happens on an agent's severity judgment without a fresh, system-recorded check — the same "evidence validated before advancing" discipline gate_engine.py applies to every Agency OS transition.
