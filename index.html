Start Here (plain English)

The problem: a solo vibe coder with a backlog of small client tickets does not need a cleverer chatbot. You need something that takes a labeled issue, plans it, builds it in isolation, runs real checks, gets it reviewed, and hands you a merged PR — without a server to babysit and without quietly merging things it should not.

The solution in today's radar: melcutz/software-factory, an autonomous, issue-to-merge software factory that runs coding agents on your own machines and coordinates the whole fleet through nothing but Git refs on your existing GitHub remote. No central server, no database, no SaaS. It is a young, tiny project — and that honesty is priced into the verdict below.

The Featured Factory: melcutz/software-factory — issue-to-merge on your own machines INVESTIGATE

  • Link: github.com/melcutz/software-factory — Python 3.10+ with zero third-party runtime dependencies (standard library only); requires Git, GitHub CLI (gh ≥ 2.67) and the Antigravity CLI (agy); OpenCode CLI optional.
  • License (verified from the LICENSE file, Nov 27, 2026): MIT (Copyright 2026 melcutz). Free for commercial use.
  • Verified repo facts: 7 stars, created Nov 13, 2026, renamed from software-factory-agy (v0.3.0 on main, untagged; latest GitHub release tag is v0.2.0). Latest commit Nov 22, 2026 (31b7688: multi-machine lessons-learned article plus a fix resolving all 20 findings of a self-run repository audit).
  • What it is (simple English): you label a GitHub issue factory. A worker claims it and drives a deterministic pipeline: plan (dependency-aware Batch-DAG with Depends on #N parsing) → intake (scope/risk classification, asks for clarification via a factory:needs-info label) → spec (1–6 ordered vertical slices) → build in an isolated git worktree with a deterministic check gate (factory/checks.sh, protected_paths) → parallel specialist reviews (code low/medium/high, plus security/ux/ui when those surfaces are touched) → approve and merge (or stop at factory:needs-human) → optional staging QA deploy train with automatic rollback.
  • The distinctive trick: zero-server multi-machine coordination. Workers on any number of machines cooperate through Git refs under refs/factory/*: atomic CAS leases for jobs, heartbeat refs with TTL so stale leases get reclaimed, shared fleet-wide rate-limit cooldowns, and factory halt/resume as a global stop button.
  • Classification: a new project (created Nov 13, 2026), currently at v0.3.0 on main. Recent change: PR #15 (merged Nov 19) added pluggable coder backends (Gemini via agy, OpenCode, OpenRouter, including free tiers), ordered fallback chains, and an optional abstain-safe local-LLM decision gate.
  • Why it matters to a vibe coder: it is a full factory you can run on the laptop and spare box you already own, with escalation-to-human and a risk-gated auto-merge limit (auto_merge defaults to "low" and can be set to "none") built in from day one.
  • Costs (real): the software is MIT and dependency-free. Model access is not: the default models run through the Antigravity CLI (agy, Gemini), which needs its own account/subscription; OpenCode and OpenRouter free-tier models are supported as alternatives. A max_job_cost_usd per-job circuit breaker and per-model pricing telemetry in factory stats help you keep the invoice visible. Staging QA needs a staging environment you host.
  • Windows compatibility: untested and not claimed by the repo. It is pure-Python stdlib plus gh, so the factory itself is plausible on Windows, but the required agy CLI's Windows availability is not documented in the README (the install notes reference Ubuntu 24.04+ pip behavior). Treat Windows as unverified; WSL2 is the safe path.

Honest Gaps

  • PROPOSAL and pricing: absent, by design. Commercial work stays in Agency OS.
  • Product-level security scanning: the security reviewer is an LLM dispatched by surface, not a scanner. No SAST, no dependency audit, no secrets scanning of your product (the leak check guards the factory's own commits, not your codebase). External filler, if verified separately: a scanner such as Semgrep could slot into the checks.sh gate — compatibility untested.
  • Young, single-author, tiny audience: 7 stars, created Nov 13, 2026, one contributor. There is no community hardening, no security audit, and the README's metrics are the author's own case studies. Treat everything as unproven until your scratch-repo run proves it.
  • Antigravity CLI dependency: the default models require agy (Gemini), a vendor-specific CLI; that is both a cost line and a lock-in. OpenCode/OpenRouter backends exist as alternatives but add setup surface.
  • Autonomous merging is real: with auto_merge at its default "low", low-risk PRs merge without a human. That is a feature and a risk; set it to "none" until you trust the gate.
  • No sandbox story: agents run on your machines with your permissions, inside worktrees. Worktree isolation protects the repo, not your filesystem. Containerization is left to you.
  • Governance: escalation labels, bounded rounds and risk thresholds are genuine guardrails, but there is no multistage gate engine or living project-state file. It complements gate_engine.py, it must never replace it.

Why It Fits Agency OS

  • Evidence before advancing: every slice must pass the deterministic checks.sh gate before review, and the approver acts on gate results plus reviewer findings — not on the builder's claim of done. That is Agency OS's "evidence validated before advancing" rule in another codebase.
  • Never invents an answer it can ask for: when intake lacks information it applies factory:needs-info and waits for a human, rather than filling gaps with plausible fiction. The optional local decision gate is explicitly abstain-safe and never rejects or escalates on its own.
  • Human approval points are structural: factory:needs-human after bounded rounds, a factory:ship label for human-approved ready PRs, and a configurable auto_merge risk ceiling. Approval is a labeled stop in the pipeline, not a suggestion.
  • Bounded effort, declared in advance: max_rounds, max_slice_retries, agent_timeout_sec, gate_timeout_sec and max_job_cost_usd are config, not vibes — stop conditions written before the run.
  • Specialized roles, orchestrated: planner, intake, spec_writer, builders, five kinds of reviewers, approver and QA agent are separate configurable roles with per-role model fallback chains — the same specialized-agents-plus-orchestrator shape as Agency OS, at a smaller scale.
  • Compatibility status: plausible, untested. Nothing indicates it reads project-state.json or speaks Agency OS gates; its gate outputs, review findings and escalation labels would enter Agency OS governance as candidate evidence only.

Limitations, Risks & Human Review

  • Immaturity is the headline risk: two weeks old, 7 stars, one author, untagged v0.3.0 on main. Expect rough edges and breaking renames (the project already renamed itself once). Pin a commit, not main, for anything resembling real use.
  • Unattended-run safety: do not point it at a client repo before a scratch-repo trial. Agents run with your user permissions; keep client credentials out of the environment and prefer a container or VM.
  • Auto-merge default: auto_merge: "low" merges low-risk PRs autonomously. For client work, set it to "none" and keep the merge decision human, exactly like Agency OS's release gate.
  • Windows: unverified. The factory is pure-Python stdlib, but the required agy CLI's Windows support is not documented; plan on WSL2 and verify factory doctor before committing to it.
  • Model costs: free-tier OpenCode/OpenRouter paths exist, but the defaults ride on Gemini via agy. Use model_pricing + factory stats and a max_job_cost_usd cap so an unattended night cannot surprise you.
  • Human review points: what you label factory (LEAD), every factory:needs-info answer, every factory:needs-human escalation, every merge on a client repository, and every production release. Never delegate those.

Test Today: a 45-minute scratch-repo-only evaluation

  • Zero-cost setup (15 min): in a scratch GitHub repo (never a client repo), clone software-factory and pip install -e . (Python 3.10+; no other dependencies). Configure the cheapest backend you have — an OpenCode/OpenRouter free-tier model keeps this genuinely $0. Run factory init, edit factory/checks.sh to run pytest, create the three labels, then factory doctor.
  • Safety-first pass (10 min): set auto_merge: "none" and max_job_cost_usd to a small number. Confirm factory doctor validates your gate script and backends before anything runs.
  • Factory pass (15 min): open a trivial low-risk issue, label it factory, run factory plan (dry-run DAG) and then factory run. Watch it: claim a lease, build in .worktrees/, run checks, dispatch a reviewer, and leave a PR ready for human merge instead of merging itself.
  • Escalation pass (5 min): file a deliberately ambiguous issue. Verify it applies factory:needs-info and asks questions instead of guessing — the exact behavior Agency OS needs from any executor.
  • Expected results: one merged-or-ready PR with gate evidence in checks.md, one factory:needs-info stop, and a factory stats cost line. If the escalation pass fails, the verdict drops to SKIP for client work.

Agency OS Integration Proposal: software-factory as the issue-to-PR executor for GitHub-hosted client repos, with its gate output as QA evidence

  • Problem solved: Agency OS's DEVELOPMENT↔QA loop currently depends on you driving the executor. software-factory automates exactly that loop end-to-end, from labeled issue to reviewed, gate-passing PR, on your own hardware.
  • Workflow improved: inside DEVELOPMENT/QA, label client-repo issues factory with auto_merge: "none". Its deterministic checks.sh results, reviewer findings and staging-QA outcomes become the evidence package the gate engine inspects; factory:needs-human escalations map to an Agency OS CEO_REVIEW task.
  • Lifecycle point: DEVELOPMENT through QA (plus optional staging QA) only. LEAD, PROPOSAL, SPECIFICATION sign-off, SECURITY decisions, RELEASE and governance stay untouched; gate_engine.py, project-state.json and human approvals are unchanged.
  • How results are validated: the gate engine reads the gate script's exit status and checks.md artifacts from the PR — deterministic outputs, not agent claims. An escalation without a recorded human answer blocks advancement, exactly as Agency OS requires.
  • What happens on failure: bounded rounds exhaust, the job escalates with factory:needs-human and the saved checkpoint, and the gate refuses to advance — a visible blocked state, not a silently merged guess.
  • Smallest safe experiment: one scratch repo, one trivial issue, free-tier models, auto_merge: "none", cost cap on. Promote to a client repo only after the escalation and human-merge behaviors reproduce reliably. Compatibility plausible/untested.

Daily Learning: "abstain-safe decisions" — a decision agent that is allowed to say 'I don't know'

  • Concept (simple English): software-factory's optional local-LLM decision gate (used only for planner, intake and approver classifications) must state a confidence; below gpu.min_confidence (default 0.9) it raises GpuAbstain and the pipeline falls through to a stronger model — and the gate is hard-restricted so it "never rejects or escalates an issue on its own." A classifier that cannot abstain will guess, and a guess at an approval gate is a silent human decision made by a model.
  • How an AI agent might get it wrong: an intake or approver agent with no abstain path always outputs an answer. Low confidence becomes a confident-looking "accept, low risk", and a high-risk change sails into auto-merge because nobody designed the "I'm not sure" branch.
  • How you recognize the failure: gate decisions with no recorded confidence; risk classifications that cluster suspiciously on "low"; escalations that only ever happen after failures, never from uncertainty; logs where the fallback chain never fired because the weak model always answered.
  • What detects it: require every automated classification in Agency OS (intake triage, QA pass/fail, release readiness) to emit a confidence and an abstain action; route abstentions to a human instead of a fallback default; let gate_engine.py reject any gate decision recorded without a confidence value. In Agency OS terms: an agent that cannot abstain should not hold a gate key.
