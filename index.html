The Production-Readiness Gap

The criticism: "Every tool can produce a working demo. None of them consistently produce production-ready software without human review." — practicing engineers and CTOs reviewing 2026's vibe-coding tools ([Justin McKelvey, fractional CTO](https://justinmckelvey.com/blog/best-vibe-coding-tools-2026)).

The industry's working definition: production readiness = the team can tell whether the application is healthy from the outside, explain a failure from the inside, and handle real users, sensitive data and an accountable lifecycle ([SDG Engineering checklist](https://www.sdg.la/guides/vibe-coded-app-production-readiness-checklist/)). A working prototype proves the idea; readiness is the engineering layer added after.

The sequence that works: testing first (unit/integration/E2E), then CI/CD that ships only tested code, then monitoring, then security audit — responsibility for readiness lies with the team that deploys, not the generator ([Slash's production checklist](https://slash.co/resources/vibe-coding-to-production-the-checklist-testing-ci-cd-monitoring-security/)).

Today's five picks map one-to-one onto that answer: architecture (bulletproof-react), infrastructure (react-starter-kit), review (px0, Lowdefy), and a measurable definition of done (Mercari's checklist). This is exactly your Agency OS governance philosophy — a project is never production-ready just because it runs.

Agency OS Integration Proposal: a verifiable production-readiness gate

  • Problem solved: "production-ready" is currently an opinion. The critics win arguments because readiness claims have no measurable definition. The fix: a checklist-driven, evidence-backed definition — which is already your governance philosophy, now with an industry-authored rubric.
  • Exact workflow improved: RELEASE gate. Today's picks fill it: bulletproof-react = ARCHITECTURE-stage standard the dev agent must follow; Mercari checklist = RELEASE-stage rubric; px0/Lowdefy = future QA/CEO_REVIEW review tooling.
  • Where in the lifecycle: ARCHITECTURE (structure standard) → DEVELOPMENT (agent builds into the skeleton, e.g. react-starter-kit) → QA (tests + human review) → SECURITY (your existing scanners: SecretSieve, Trivy) → RELEASE (checklist rubric).
  • Inputs: the pruned Mercari checklist (small-business-relevant items only), the project's evidence artifacts (test reports, security scans, monitoring config).
  • Outputs: a per-release readiness artifact in project-state.json: each checklist item marked VERIFIED (with evidence link) / UNVERIFIED / BLOCKED.
  • How results are validated: evidence validated before advancing — an item is VERIFIED only with a dated artifact attached; agents may never self-mark items without the artifact (your REAL/SIMULATED/ASSUMPTION rules apply).
  • What happens on failure: missing evidence blocks the RELEASE stage in the gate engine; a waiver (shipping with a known gap) is a commercial/risk decision → human approval required. No change to the gate engine itself — this feeds it.
  • Smallest safe experiment: take 10 checklist items relevant to a small-business web app (auth, secrets, dependencies, backups, monitoring, error handling, rollback…), run one current project through them by hand, and mark each VERIFIED/UNVERIFIED/BLOCKED. That artifact is your first honest readiness report — and the beginning of your rebuttal to the critics.

Daily Learning: "production-ready" is a claim about operations, not about code quality

  • Concept (simple English): production-ready doesn't mean "the code is good." It means: you can tell from the outside whether the app is healthy (monitoring), you can explain why it failed from the inside (logs/traces), you can recover quickly (rollback/backup), and you can account for what it did (audit). A bug you can detect, explain, and roll back is a production incident; a bug you can't see is an outage.
  • How an AI agent might get it wrong: the agent equates "all tests pass" with "production-ready" and marks the release VERIFIED — ignoring observability, backups, rollback and incident response, which no unit test covers.
  • How you recognize the failure: a VERIFIED readiness claim with no artifacts for monitoring, error handling, data backup, or rollback — the checklist items with empty evidence slots expose it immediately.
  • Which tool/test detects it: the Mercari production-readiness checklist turned into a gate rubric — its observability/incident-response items fail loudly when evidence is missing; pair with your existing prepush_release_check.ps1 so a release without those artifacts never reaches the push.
