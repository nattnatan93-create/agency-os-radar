The problem: a one-person AI agency can collect dozens of agent tools, but they don't connect — one brainstorms, another tests, another merges, and the human glues them together every day. The glue work is what sinks a solo vibe coder.

  • No general governance layer: no project-state.json equivalent; its governance is scoped to merges (protected_paths, required_checks), not a full lifecycle state machine. It complements gate_engine.py — it never replaces it.
  • Explicitly refuses taste judgment (VERIFIED): "a green gate never means the product is good. It means the layer a machine can check is intact." — matching Agency OS's rule that passing tests ≠ production-ready.

Why It Fits Agency OS

  • No invented facts: the backlog is never invented; discovery can only publish verified findings — the same VERIFIED-before-advancing rule Agency OS enforces.
  • Evidence before advancing: the merge gate merges only what the defects-seen record supports, and evidence is verified by script before the next step.
  • Leak accounting: the holdout fence counts every scenario exposure in holdout-exposures.jsonl — an audit trail of agents peeking at the answer key.
  • Human approval points: what to build (PRD/issues), what it must never become (MISSION.md), the first watched lap, and staging judgment stay human — matching Agency OS's human-approval rules.
  • Agency OS compatibility: plausible — untested. Nothing here replaces gate_engine.py or governance; it is a pattern source, and its code is unlicensed.

Limitations, Risks & Human Review

  • Missing license (the big one): no LICENSE file on main as of today — default copyright. Local experiments fine; do not copy its code into client deliverables until a license appears. His Archon repo is MIT, but that does not license this repo's code.
  • Unattended autonomy risk: leave scheduling off until you have watched one full lap; run the first lap with merge=approve so the reviewer approves instead of merging.
  • Token cost: laps drive your coding agent's model; instrument tokens on day one, use medium models for routine work.
  • Harness-specific fence: the holdout fence is a Claude Code hook; a factory running Codex or Pi has no fence — the holdout must live outside the repo (VERIFIED from README).
  • Windows timer runs only while you are logged on — a factory that only runs while your laptop is open is a demo, per the README's own warning.

Agency OS Integration Proposal: the holdout + calibration pattern for the QA gate

  • Problem solved: QA evidence can be gamed by the same agent that wrote the code, because it knows which cases will be checked.
  • Exact workflow/agent it improves: the QA agent's evidence production — feeding, never replacing, gate_engine.py and precommit_check.py.
  • Where in the lifecycle: QA (with outputs that strengthen CEO_REVIEW review packs).
  • Inputs: the product document/PRD. Outputs: independent black-box scenarios, a verification record, and a leak log counting any agent that saw a scenario.
  • How results are validated: the factory's own calibration triple — baseline verified, a deliberate relevant fault FAILS, a wrong-identity check is inconclusive. A holdout suite that cannot fail a deliberate fault is broken and stays UNVERIFIED.
  • What happens on failure: the QA gate stays BLOCKED; an escaped defect becomes a new holdout scenario — the same maintenance loop the factory itself uses.
  • Gate or human approval? Neither changes: evidence feeds the existing QA gate; governance untouched.
  • Smallest safe experiment: the repo is unlicensed, so do not copy its code — implement the pattern yourself: write your own HOLDOUT.md for one existing project, a small verification script only the QA gate can call, and add the three calibration checks to a copy of precommit_check.py on a test branch. Observe one run; no gate-engine changes.

Daily Learning: holdout verification and calibration

  • Concept (simple English): keep a set of test scenarios the builders can never read, so verification stays independent. Prove the verifier itself works by calibration: it must pass a good baseline, FAIL a deliberately broken build, and stay inconclusive on a wrong app.
  • How an AI agent might get it wrong: the implementing agent discovers the test cases and optimizes only for them (teaching to the test), or the verifier "passes" because it never exercised a real user transition.
  • How you recognize the failure: suspiciously perfect scores with no defect history; a verifier that has never failed anything.
  • Which tool/test detects it: the calibration triple (a verifier that can't fail a deliberate fault is broken) — plus the factory's exposure log pattern, which counts who peeked at the answer key.
