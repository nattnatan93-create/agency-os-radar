The Production-Readiness Gap

The criticism: "AI-built apps aren't production-ready" is usually an evidence problem. An agent saying "the AI feature works" or "I remember the client's requirements" is a claim. Production-ready means: AI behavior is regression-tested against approved examples, prompts can't silently break, agents can prove what they did, and knowledge survives the switch from one agent to the next.

Today's answer: promptfoo makes AI outputs testable in CI with pass/fail evidence and AI red-teaming; OpenCode 2.0's SDK turns the coding agent itself into an auditable, embeddable component; ai-memory makes agent memory a plain, diffable, human-readable git artifact; google/skills packages repeatable know-how as reviewable components instead of buried prompts.

Why this maps to Agency OS: your governance already demands VERIFIED evidence and distinguishes REAL/SIMULATED/ASSUMPTION. Today's tools are external evidence producers — eval reports, git-backed memory, session records — that your gate engine can consume. They feed your governance; none replace it.

Top 5 Discoveries

1. OpenCode 2.0 — flagship open-source AI coding agent, now embeddable TEST NOW

  • Link: github.com/anomalyco/opencode
  • What it does (simple English): an open-source AI coding agent that works in the terminal, desktop, and web — it reads your code, makes edits, runs commands, and explains what it did.
  • What changed recently and when: version 2.0 launched Oct 16, 2026: background agents (subagents work while the main agent continues), "Code Mode" (agents write scripts that combine MCP servers and OpenAPI endpoints in one flow), a rebuilt server API, a new @opencode/client package, and an @opencode/sdk for embedding OpenCode into custom apps. Breaking change: 1.0 plugins and the old server API are incompatible. (VERIFIED: repo active today — last push Oct 22; release coverage from launch news.)
  • Why it matters to a vibe coder: the SDK means the coding agent stops being a fixed app and becomes a component your orchestrator could spawn, supervise, and audit — the exact shape of Agency OS's dev agent.
  • License & costs: MIT (VERIFIED from the repo license). The tool is free; the models it calls are not — you bring your own provider keys/subscriptions, so cost depends on your plan. Open source ≠ free model access.
  • Windows & install: TypeScript project; terminal-first with a desktop app also available. Get install steps from the official repo/docs only — never from third-party mirrors.
  • Agency OS fit: DEVELOPMENT stage dev agent, or an embeddable engine behind your orchestrator. Compatibility: plausible — the SDK/API could integrate with your orchestration; untested with gate_engine.py or project-state.json.
  • Evidence/output: session records of edits, commands run, and diffs — reviewable history of what the agent actually did.
  • Limitations/risks/human review: 2.0 has breaking changes (plugins from 1.x won't work); agent edits still require your QA gates — "the agent wrote it" is not evidence of correctness; model subscription costs are yours.
  • Verdict: TEST NOW — major, well-documented release of the category leader in open-source coding agents.

2. promptfoo — regression tests and red-teaming for AI apps, now part of OpenAI TEST NOW

  • Link: github.com/promptfoo/promptfoo
  • What it does (simple English): a CLI that runs your AI prompts and agents against a fixed set of test cases and scores the answers — so when a prompt or model changes, you find out what broke in seconds, in CI, instead of hoping nothing did. It also runs AI red-team scans (jailbreaks, injection, OWASP LLM presets).
  • What changed recently and when: v0.124.0 released Oct 6, 2026; repo active today (last push Oct 22, VERIFIED). The project was acquired by OpenAI (announced March 2026) and the repo remains MIT-licensed open source.
  • Why it matters to a vibe coder: every AI app your agency ships has prompts. promptfoo turns "the AI seems fine" into a dated pass/fail artifact — and its red-team scans give your SECURITY stage something real to check before release.
  • License & costs: MIT (VERIFIED from the repo license). Free; runs against your model provider using your own API key (usage costs apply), and supports provider-free self-tests (echo provider) for CI plumbing with zero model calls.
  • Windows & install: Node.js CLI — npx promptfoo@latest — also installable via npm, pip, or brew. No special hardware.
  • Agency OS fit: QA stage (AI-feature regression evidence) and SECURITY stage (AI red-teaming before release). Compatibility: plausible — JSON/HTML results are gate-engine friendly; untested with your scripts.
  • Evidence/output: dated eval results (JSON/HTML) with pass/fail per test case, plus structured red-team findings reports.
  • Limitations/risks/human review: LLM-as-judge scores are non-deterministic — prefer deterministic assertions, treat judge scores as advisory; red-team scans send your prompts to your model provider — check data handling before using client data; a passing suite proves covered cases, not overall safety.
  • Verdict: TEST NOW — free, Windows-friendly, testable today with zero model spend.

  • What changed recently and when: very active — last push Oct 22, 2026 (today, VERIFIED from the repo), ~12.6k stars; it was a top trending repo the week of Oct 17, 2026 in trending analyses. Specific release dates were not individually verified today.
  • Why it matters to a vibe coder: Agency OS's orchestrator coordinates specialized agents — discovery, spec, dev, QA, security. Their shared context currently lives (if anywhere) in project-state.json. A git-backed, human-readable memory layer is the same problem solved once, and its diffs are reviewable evidence.
  • License & costs: MIT (VERIFIED from the repo license). Free; local-first, no subscription. No external API dependency for storage (markdown + git).
  • Windows & install: Rust-powered tool distributed as a binary — check the official repo README for the current Windows route before installing. Verify binaries come from the official repo only.
  • Agency OS fit: orchestrator coordination and MAINTENANCE stage (context across sessions). Compatibility: plausible — memory as markdown files is portable and could complement project-state.json; untested.
  • Evidence/output: a diffable markdown knowledge base — every memory addition is a commit you can review, reject, or attribute.
  • Limitations/risks/human review: agents writing to shared memory can record unverified claims as if they were facts — your REAL/SIMULATED/ASSUMPTION discipline must apply to memory contents too; never let client secrets land in memory files; newer project — pin versions and review what it stores.

5. SecureVibeCoded / Hacktoberfest-CommitShield (svc) — change-aware pre-commit secret scanner INVESTIGATE

  • Link: github.com/yashselokar2025/Hacktoberfest-CommitShield
  • What it does (simple English): a pre-commit hook that sits on top of Gitleaks and only alerts on newly introduced secrets (tracking findings in a local SQLite baseline), optionally using a local Gemma model via Ollama to judge borderline tokens — aiming to kill alert fatigue without letting real keys through.
  • What changed recently and when: brand new — repo created Oct 17, 2026 (VERIFIED from the repo; MIT license). It's a Hacktoberfest 2026 challenge submission published this month, with an install.ps1 for Windows and a Next.js showcase site.
  • Why it matters to a vibe coder: the design directly addresses your daily reality — agents generate lots of code with lots of tokens, and a scanner that cries wolf on every commit gets disabled. The change-aware NEW/EXISTING/RESOLVED baseline is a pattern your precommit_check.py could adopt even if you never install this tool.
  • License & costs: MIT (VERIFIED from the repo license). Free; core scanning is offline-capable (Gitleaks rules + local SQLite; Gemma via local Ollama with a rule-based fallback).
  • Windows & install: Python/pip install from the git repo, with a Windows install.ps1 script provided. Note: pip-installing from a five-day-old repo is a supply-chain risk — see below.
  • Agency OS fit: SECURITY stage pre-commit (secrets). Compatibility: plausible pattern for precommit_check.py; the tool itself is UNTESTED and too immature to trust as-is.
  • Evidence/output: pre-commit block/pass decisions plus a SQLite findings baseline; the concept of a machine-checked "no new secrets" statement is exactly the evidence type your SECURITY gate wants.
  • Limitations/risks/human review: its accuracy claims (e.g., F1 = 0.950, ~8% false positives) are SELF-REPORTED and UNVERIFIED — treat as claims, not facts; a 2-star, week-old hackathon project with install scripts must be code-reviewed before you run anything; running an LLM over your diffs means diffs pass through that model — keep it local (Ollama) and never point it at client secrets.
  • Verdict: INVESTIGATE — study and borrow the pattern today; do not install blindly.

When you're ready, add one real test using your existing model API key.

Daily Learning: golden-dataset regression testing for AI behavior

  • Concept (simple English): a "golden dataset" is a small, fixed set of input/expected-output examples you and the client agreed are correct. Regression testing means every time the code (or prompt, or model) changes, you re-run the whole set and compare — so "still works" is measured, not remembered.
  • How an AI agent might get it wrong: the agent tests its own new output with an LLM judge that scores leniently (or is the same model family), quietly changes the expected outputs to match the new behavior ("the test was outdated"), or declares the feature stable after trying two or three informal examples instead of the agreed set.
  • How you recognize the failure: eval results vary run-to-run with no fixed dataset; test files were modified in the same commit as the feature; "the AI works" claims carry no dated artifact with a case-by-case pass/fail.
  • Which tool/test detects it: promptfoo — a committed golden dataset with deterministic assertions makes each case pass or fail mechanically; judge-style scores are visible as advisory only. Diff review catches expected-output tampering: the golden set changes only with human approval, exactly like your waiver rule.
