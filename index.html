Start Here (plain English)

The problem: a vibe coder can plan a project with Claude Code, but turning that plan into merged, reviewed, CI-passing pull requests still means hand-running every step: writing tickets, launching sessions, chasing builders, reviewing diffs, running CI and deciding what merges. Do it alone and the crew stops the moment your terminal closes; do it with several agents and nothing records who decided what, or why.

The solution in today's radar: Tares, an open-source platform for always-on AI agents with a Software Factory edition: a crew of Claude Code sessions on your own machine takes a project from a spec to pull requests merged on main. An orchestrator hands out tickets, builders open PRs in parallel, a reviewer holds every change to a fixed bar, and a change merges only once it passes review and CI. Tickets, reviews, decisions and your answers stay recorded on Tares, so the crew carries on after a restart and you can audit every choice later.

Honest Gaps

  • PROPOSAL / client artifacts: no quotes, proposals or client-facing documents; the spec is internal.
  • SECURITY (code-level): guardrails enforce policy at hook points, but nothing scans generated code for vulnerabilities. A dedicated scanner such as Semgrep is the classic gap-filler; treat as a candidate to verify separately, not as verified advice.
  • RELEASE/deployment: the factory ends at merge to main; nothing builds a deployable artifact or deploys it.
  • LEAD / DISCOVERY: assumes you arrive with a project to plan; no lead qualification or discovery workflow.
  • Gate engine: no project-state file, no lifecycle transition enforcement, no gate rollback engine. Its reviewer verdicts, guardrail decisions and merge queue approvals are the raw material for gate evidence, not the gates themselves.

Why It Fits Agency OS

  • Specialized agents coordinated by an orchestrator: exactly the Agency OS shape, built in: an orchestrator hands out tickets, builders own one milestone and repo each, a reviewer enforces a fixed bar, and a merge queue serializes what lands.
  • Agents must never invent facts or approvals: a change merges only when review, CI and guardrails together answer merge_ready; the reviewer's verdict is posted as the cell's GitHub App so it exists as a system record, not an agent's claim; stations refuse to start without rules.
  • Evidence validated before advancing: milestones have acceptance checks, the reviewer holds every change to a fixed bar, required CI checks are enforced, and tickets, reviews and decisions persist for audit.
  • Human approval points: the first crew run asks how far it may go; the console shows what waits for you; merge-queue approval and the bounce ladder keep consequential decisions human. You talk to one session, only for decisions that are yours.
  • Living state: tickets, reviews, crew calls and your answers live on Tares and survive restarts, and the Second Brain keeps decisions indexed for the next reader, the control-plane equivalent of an authoritative state file.
  • Compatibility status: plausible, untested. Nothing in the docs shows Tares reads project-state.json or enforces Agency OS lifecycle transitions, so it complements gate_engine.py and never replaces it.

Limitations, Risks & Human Review

  • One-person limit on self-hosted: without an enterprise license key, a self-hosted Tares runs for one person; team features need Tares Cloud or an enterprise license. Fine for a solo agency, a real cost if you grow.
  • Hard dependency on Claude Code: the factory crew is made of Claude Code sessions on a plan with background sessions, plus gh with write access to your repos. No Claude Code subscription, no factory.
  • Young project, low stars: 47 stars and heavy daily churn (a bash engine removed, engines swapped to Python within weeks). Pin a stable release, read each changelog, and expect breaking changes; the maintainers even enforce schema-version bumps for breaking changes, which is a good sign.
  • Unattended crews spend real tokens: builders run in parallel on background sessions; cap spend with your Claude plan limits, start with one small project, and keep the "how far may I go" answer conservative.
  • Guardrails are new: readable rules and hook points land in the v1.58.0 release candidates; verify their block/warn behavior yourself before trusting them as a security control.
  • Windows is engineered-for but untested here: Windows CI is green and this week's fixes target Windows specifically, yet nothing here has been run on this PC. Budget time for first-run friction.

Agency OS Integration Proposal: Tares crew as the governed DEVELOPMENT→QA→merge execution layer

  • Problem solved: Agency OS specifies and gates well, but the DEVELOPMENT→QA→merge stretch is manual today: who builds, who reviews, what CI must say before merge. Tares supplies exactly that stretch with parallel builders, a fixed-bar reviewer, required CI and a merge queue.
  • Workflow improved: DEVELOPMENT and QA execution — an approved Agency OS specification becomes a Tares spec with milestones and acceptance checks; the crew builds, reviews and merges.
  • Lifecycle point: SPECIFICATION (spec, milestones, tickets) → DEVELOPMENT (builders) → QA (reviewer + CI) → RELEASE (merge queue to main).
  • Inputs and outputs: an approved Agency OS specification in; merged PRs, review verdicts, CI results, guardrail decisions and a durable decision record out.
  • How results are validated: gate_engine.py treats Tares review verdicts, CI results and merge-queue approvals as candidate evidence only; QA evidence still comes from your own test runs, and a human confirms before any gate advances. A merged PR is never sufficient evidence on its own.
  • What happens on failure: failed CI or a reviewer send-back bounces the ticket back to the builder (with a bounce ladder to the orchestrator, then your desk); gate rollback behavior is unchanged — nothing auto-advances because a PR merged.
  • Gate or human approval: it feeds existing gates and replaces nothing (gate_engine.py, advance_gate.ps1 unchanged). CEO_REVIEW, scope changes, waivers, client acceptance and release stay human.
  • Smallest safe experiment: today's scratch-repo run: one trivial spec, one milestone, conservative permissions. Zero changes to Agency OS scripts; if the review + CI + merge evidence is useful, pilot one real project's DEVELOPMENT stage through a local Tares.

Daily Learning: "merge_ready" — one answer instead of three opinions

  • Concept (simple English): Tares computes a single merge_ready verdict per change from three independent sources: the review gate, CI checks and guardrails. No single voice, including the builder agent, can merge; the change lands only when all three agree.
  • How an AI agent might get it wrong: a builder reports "tests pass, ready to merge" from its own reading of the logs, a reviewer agent skims the diff and agrees, and the change merges on two agents' word with nothing executed. Independent evidence channels collapse into one agent's opinion.
  • How you recognize the failure: merge decisions with no CI run attached; review verdicts that quote the builder's own summary; "green" claims with no recorded check IDs; the same agent both producing and approving the work.
  • What detects it: a gate rule that every advance requires evidence from independent, system-recorded sources (executed CI, a separate reviewer, guardrail logs), never an agent's prose claim — the same "evidence validated before advancing" discipline gate_engine.py applies to every Agency OS transition.
