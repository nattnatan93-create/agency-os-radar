Daily open-source discoveries for a one-person AI software agency

Start Here (plain English)

The problem: an AI coding agent does different work every run. Ask it to fix a bug twice and you may get a plan one time and a rushed patch the next. A one-person agency cannot supervise every step of every agent, so either quality slips or you become the bottleneck.

The solution in today's radar: coleam00/Archon is an open-source factory builder: you write your delivery process once as a YAML workflow, and Archon runs it the same way every time — agents supply judgment inside each step, scripts make the mechanical decisions, and a run pauses and comes to you only when it needs a decision you own (approvals, scope changes). It ships with a working software factory (the sdlc pack): issue in, merged pull request out, with approval gates, a full event log and per-run costs stored in your own database.

The Featured Factory: coleam00/Archon TEST NOW

  • Link: github.com/coleam00/Archon · docs archon.diy/docs
  • What it is (simple English): you describe how work should get done as YAML workflows; Archon runs them with AI agents (Claude Code, Codex, Pi — through their own CLIs and your own subscriptions), scripts, and human decisions where needed. The bundled SDLC pack is a working factory: you open an issue, archon-intake decides what it needs, the build queue runs archon-ship (plan, implement, review through specialist lenses, fix findings, wait for CI), the merge queue lands clean, review-ready PRs, unclear questions become single "attention items" with recommendations, and side discoveries get filed instead of lost.
  • What changed recently and when (VERIFIED from commit history): releases v0.13.0 (Oct 28), v0.13.1 and v0.13.2 (Oct 29, 2026), Homebrew formula updated Oct 29, plus commits on Nov 1–2, 2026 (including "Preserve host workflow results when Docker image inventory fails" and a build-queue fix that stops relaunching a PR that changed nothing). So: recent release wave within the last 5 days, and commits within the last 24 hours.
  • Why it matters to a vibe coder: this is the engine under the factory featured earlier (ai-software-factory pins an exact Archon revision). Archon gives you the three things Agency OS is built on, as product features: fixed step order (the workflow fixes the steps, checks and gates), evidence (full event log and transcript per run, stored in your own SQLite/PostgreSQL), and human-on-the-loop approvals. The README also reports it builds itself: of 524 PRs merged into the repo Oct 1–19, 2026, Archon runs built 363.
  • License & costs (verified): MIT License (verified from the LICENSE file today). The code is free. Running it is not automatically free: it drives Claude Code / Codex / Pi through your existing accounts and subscriptions, and every agent call costs what your plan/API charges (per-run cost is recorded in Archon's own database). Self-hosted on your machine — no cloud fee, no vendor platform fee.
  • Windows compatibility & install (verified): official Windows installer published by the project: irm https://archon.diy/install.ps1 | iex (PowerShell), alongside macOS/Linux (curl … | bash) and Homebrew. A Sep 1, 2026 commit specifically fixes Windows console handling ("hide the console for every subprocess exec on Windows"), so Windows is an actively maintained target — but full-factory behavior on Windows is plausible, untested by us. Prerequisites: git, and at least one coding-agent CLI (Claude Code or Codex) installed and signed in; SQLite by default.
  • Privacy note: Archon sends anonymous telemetry (workflow names only for bundled workflows, categorical run shape/outcome, no message content, "No PII, ever" per the README). Keep this in mind for client work; check the config options for opting out.
  • Verdict: TEST NOW — MIT, official Windows installer, local SQLite, uses the AI subscription you already have, and safely testable in a scratch repo.

Honest Gaps

  • No LEAD / PROPOSAL: it consumes issues that already exist. Client discovery, pricing and proposals remain Agency OS work.
  • No SECURITY stage: nothing in the SDLC pack scans secrets, dependencies or authn/authz before merge. The biggest gap for a security-gated agency. Yesterday's verified gap-filler still applies: Amal-David/keyleak-detector (MIT, per yesterday's verification) for exposed-key/RLS-misconfig detection; pair it with your existing dependency/secret checks in gate_engine.
  • No runtime/UAT verification by default: the pack stops at merged PRs + CI. (Driving a running app with recorded evidence is what the separately featured ai-software-factory adds on top, via Archon's runtime-verification workflows.)
  • Forge support today is GitHub-centric: the pack works through the GitHub CLI (gh); other hosts go through the plugin route.
  • Fast-moving: three releases in two days (Oct 28–29) and commits landing daily — pin a version before depending on behavior.

Why It Fits Agency OS

  • Fixed process, judgment inside steps: the workflow fixes the order, checks and gates; the agent only supplies judgment — the same philosophy as Agency OS's gate engine being authoritative over the agents.
  • Human approval at the boundary: approval-gate nodes pause the run and present one decision with a recommendation — matching your rule that commercial decisions, scope changes and releases need human approval.
  • Evidence before advancing: every run has a full event log and transcript in your own database; loop nodes decide "done" by running your test command, not by asking the agent. This matches your validated-evidence rule.
  • Living project state: durable run state, queues, and answers written back into the issue — philosophically aligned with project-state.json being authoritative. It complements, never replaces, your gate engine.
  • Costs visible per run: every run's cost is recorded — the accountability you want before charging a client project.
  • Agency OS compatibility: plausible — untested. Nothing here is proven alongside your existing gate_engine.py / PowerShell stack on your Windows PC; the integration proposal below stays additive.

Limitations, Risks & Human Review

  • It runs your coding agents with real account spend: a loop node with max_iterations: 10 can make many model calls before it stops. Set iteration caps and start with cheap models/tiers; treat per-run cost reports as mandatory reading.
  • Auto-merge capability exists: the merge queue can land PRs without you reading them. For client work, keep every merge behind an approval gate or branch protection requiring review — and treat any auto-merge adoption as a commercial decision requiring your CEO_REVIEW approval.
  • Unattended runs are powerful: isolated worktrees make parallel unattended work safe for the repo, but not for secrets — keep credentials out of scratch repos, and never give any tool unrestricted access to client data.
  • Telemetry is on by default: anonymous but real; check configuration before using it inside a client engagement, per your own data-protection rules.
  • Script-safety: the installer is a remote script (irm … | iex). Read the install.ps1 first — the same rule you already apply to never execute untrusted code blind.
  • Not a security tool: keep your own security stage (secrets, dependencies, authn/authz) — see gaps.

Agency OS Integration Proposal: a "done = the script says so" QA loop + approval attention items

  • Problem solved: today a dev or QA agent in Agency OS can declare "tests pass" in prose; you have no machine-checked loop bound (implement → verify → fix) and no single place where a run pauses for your decision with the evidence attached.
  • Workflow/agent improved: the dev agent's build loop and the orchestrator's approval hand-offs — feeding, never replacing, gate_engine.py.
  • Lifecycle stage: DEVELOPMENT → QA (loop), CEO_REVIEW (approval item).
  • Inputs: the approved spec/plan from project-state.json; the project's real test command. Outputs: a machine-decided loop outcome (test command exit code, iteration count), a full run transcript, per-run cost, and a single approval item with a recommendation.
  • How results are validated: the loop's "done" is the exit code of your own test command (until_bash) — the agent's claim is irrelevant; the approval decision is a logged event; the gate engine still consumes project-state.json exactly as before.
  • What happens on failure: tests never pass within max_iterations → the run fails with a categorical failure class and the transcript shows which node failed; a rejected approval cancels the run and nothing advances.
  • Gate or human approval? Neither replaces anything: gate transitions and rollback stay untouched. Merging anything for a client stays behind your human approval rule — the Archon approval node is the natural place to surface it, but the approval is yours, not Archon's.
  • Smallest safe experiment: in a scratch Agency OS project, write the README's example build-feature.yaml (plan → implement loop with until_bash = your pytest command, max_iterations: 3 → approve wait). Run it once, approve it, run it again and reject it. Compare the two transcripts against what gate_engine.py records for the same work — then decide whether the loop pattern is worth adopting.

Daily Learning: the loop that ends when the script says so

  • Concept (simple English): an agentic loop should not end when the agent says "done" — it should end when an objective check (a test command, a validator exit code) says so, with a hard iteration cap as the backstop. The agent's judgment chooses what to try next; the script decides when to stop.
  • How an AI agent might get it wrong: it reports "all tests pass" based on its memory of a previous run, on a partial run, or on tests it quietly weakened — and a human reading the summary cannot tell the difference from a real green run.
  • How you recognize the failure: the "passing" claim has no fresh command exit code, timestamp or transcript attached; tests fail when you run them yourself; the diff touches test files without a stated reason.
  • What detects it: Archon's until_bash loop runs the actual test command each round and records the result in the run's event log. In Agency OS today, the same failure class is caught by your precommit/prepush scripts re-running checks — and the fix to copy from Archon is binding the QA exit to a recorded exit code, not the agent's sentence.
